# 0029. 段階 3 は ACL を全許可のまま切り替え、絞るのは別の日にする

- ステータス: 採用（未適用）
- 日付: 2026-11-10

## 背景

段階 3 の当日の手順は、ACL を最初は全許可にして疎通を確かめ、同じ日のうちにログを見ながら許可表（[通信ポリシー](../architecture/08-vlan-design.md#通信ポリシー)）の内容に絞る計画だった。

[ADR-0028](0028-defer-management-vlan10.md) で、管理系を段階 3b まで今の LAN（VLAN1）に残すことにした。そのため、許可表の「Management」を「今の LAN」に読み替えた ACL と、緊急用の入口（VLAN10 の緊急用プールの代わり）が、段階 3 の前に決めることとして残った。

ACL を絞る作業は時間がかかる。絞りすぎると、Caddy 経由の管理画面や Prometheus の取得が止まる。住所の付け替えと同じ日に行うと、何かが止まったとき、原因が住所の変更か ACL かを切り分けにくい。

## 決定

- **段階 3 の当日は、ACL を全許可（ルールを作らない、または有効にしない）のまま、VLAN と住所を切り替える。** 当日は、ACL を絞らない。
- **ACL を許可表の内容に絞るのは、段階 3 のあと、別の日に行う。** 目安は、段階 3 のあと数日動かして落ち着いてから。**遅くとも段階 4（IoT・Guest の SSID を分ける）の前**に済ませる。
- 今の LAN の ACL と、緊急用の入口は、段階 3 の前提から外し、ACL を絞る日の前提にする。

## 理由

- 全許可の VLAN は、今の 1 つのネットワーク（分離なし）と同じ状態で、今より悪くならない。
- 全許可の間に守る相手が、まだいない。Guests の SSID は段階 4 まで作らない。DMZ には何も置かない。Wi-Fi の端末は、段階 4 まで Trusted に入る。
- 当日、何かが止まったときの原因が、住所の変更だけに絞れる。当日の作業時間も短くなる。
- 段階 3 の前の準備が減る（今の LAN の ACL の設計と実機での確認）。

## 代替案

| 案 | 長所 | 短所 |
| --- | --- | --- |
| 当日、全許可で始めて、同じ日に絞る（従来） | 分離のない期間が数時間で済む | 当日が長くなる。止まったときの原因を切り分けにくい。今の LAN の ACL を段階 3 の前に決める必要がある |
| 当日は全許可、絞るのは別の日（採用） | 当日が短い。原因を切り分けやすい。段階 3 の前の準備が減る | 分離のない期間が数日続く |
| 段階 3 の前に ACL を完成させ、当日から絞った状態で有効にする | 分離のない期間がない | 住所の変更と ACL の不具合が同時に出る。事前に本番と同じ通信で試せない |

## 影響と再検討の条件

- 全許可の間は、VLAN を分けても、VLAN の間の通信は制限されない（リスクを受け入れる）。ゲートウェイの ACL は、どのルールにも一致しない通信を暗黙に許可するので、ルールを作らない状態が全許可になる。リハーサルの `rh-` のルールは、無効のままにする。
- 全許可の期間を延ばさない。段階 4 の前に、ACL を絞り終える。段階 4 より先に、IoT の端末を有線で IoT の VLAN に置く、DMZ に何かを置く、などで守る相手ができたときは、その前に絞る。
- 全許可の間は、`vm-infra` が止まっても、Trusted の端末から管理系に IP で届く。緊急用の入口は、ACL を絞る日までに決めて、確かめる。
- ADR-0028 の「段階 3 の前に決めること（未決）」のうち、今の LAN の ACL と緊急用の入口は、ACL を絞る日の前に移る。
