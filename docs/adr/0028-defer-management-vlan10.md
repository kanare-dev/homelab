# 0028. 段階 3 では管理系を今の LAN に残し、VLAN10 化は別の段階にする

- ステータス: 採用（未適用）
- 日付: 2026-11-09

## 背景

段階 3 は、全ホストの住所を一斉に付け替える計画で（[ADR-0004](0004-vlan-cutover-all-at-once.md)）、管理系（Proxmox ホスト、`vm-omada`、ER605・SG2210P）も同時に Management（VLAN10）へ移す設計だった（[ADR-0023](0023-proxmox-trunk-all-tagged.md) など）。

リハーサルの C-2（2026-11-09）で、次のことが分かった。

- 機器（ER605・SG2210P）は、採用されたときのコントローラーの住所（`192.168.11.12`）を覚えている。コントローラーの「コントローラーホスト名/IP」は、メールとポータル用で、機器の接続先ではない。
- 採用済みの機器の Web UI は入れず（403）、SG2210P は SSH も閉じている。Discovery Utility は Mac で動かない（同梱の JavaFX が Windows 用）。
- つまり、`vm-omada` の住所を変えたときに機器の接続先を直す手段が、まだない。付いてこないと、機器がコントローラーを見失い、ER605 のリセットと再採用（インターネットが止まる）になりうる。

運用者は、一斉切り替えにこだわりはなく、最終的には管理系を VLAN10 にしたい、という意向を示した。

## 決定

- **段階 3 では、管理系を今の LAN（VLAN1、`192.168.11.0/24`）に残す。** Proxmox ホスト（`192.168.11.10`。`vmbr0` は VLAN-aware にするが、IP とタグなしは変えない）、`vm-omada`（`192.168.11.12`、タグなし）、ER605（`192.168.11.1`）、SG2210P（管理 VLAN は VLAN1 のまま）の住所を変えない。
- **そのほかは、予定どおり一斉に切り替える**（ADR-0004）。`vm-infra`・`vm-monitoring`・`vm-apps`・`vm-code` を VLAN20、`vm-dev` を VLAN40、端末を VLAN30・50 へ。
- **管理系を VLAN10 へ移す作業は、段階 3 のあとの「段階 3b」として、別に行う。** 最終形は、ADR-0022・0023・0025 のとおり（Proxmox ホストは `vmbr0.10`、`vm-omada` は `10.77.10.3` など）。段階 3b の前に、機器の接続先を直す手段（できれば、IP ではなくホスト名にする）を整える。
- 今の LAN（VLAN1）は、段階 3b が済むまで消さない。ER605 に作った Management（VLAN10）は、段階 3b まで使わない。

## 理由

- C-2 が、段階 3 の本番に要らなくなる。機器の接続先が変わらないので、機器がコントローラーを見失うおそれがない。
- 本番で一番怖い作業のひとつ、Proxmox ホストの `vmbr0.10` への移動（物理コンソールが要る）も、段階 3 から外れる。
- 失敗したときの影響が分かれる。段階 3b の失敗は管理系だけで、ほかの VLAN は動き続ける。段階 3b には期限がなく、時間のあるときに行える。
- 最終形は変わらないので、設計の方針（VLAN の数、アドレス体系、許可表）は、そのまま使える。

## 代替案

| 案 | 長所 | 短所 |
| --- | --- | --- |
| 管理系も一斉に切り替える（従来） | 住所の付け替えが 1 回で済む | C-2 が未解決のまま、本番で当たる。失敗の影響が全体に及ぶ |
| 管理系を段階 3 から外す（採用） | 本番のリスクが下がる。段階 3b を期限なしで進められる | 段階が 1 つ増える。ACL などを「管理系は VLAN1」で作り、あとで VLAN10 に書き直す |
| VM を 1 台ずつ段階移行する | 1 回の影響が小さい | 旧・新の二重管理（DNS、Tailscale の経路、ファイアウォール）。ADR-0004 が避けた複雑さ |

## 影響と再検討の条件

- ADR-0004（一斉切り替え）と ADR-0023（Proxmox は全 VLAN をタグ付き）は、置き換えない。最終形と、一斉切り替えの方針は有効で、**段階 3 に含める範囲と、ホストが `vmbr0.10` へ移る時期だけが変わる**（段階 3b）。
- 段階 3 の間は、p2 の untagged VLAN1 を、ホストと `vm-omada` が使う。ADR-0023 の「タグなしの通信は、どこの VLAN にも入らない」は、段階 3b まで成り立たない。Terraform の `vlan_id` は必須のままにし、`vm-omada` は、タグなし（VLAN1）を明示する。`vlan_id` を付け忘れた VM は、VLAN1（管理系）に入る。
- 管理系が VLAN10 に隔離されない期間が、段階 3 のあとも続く。
- ACL は、段階 3 では「管理系 = 今の LAN（VLAN1）」で作り、段階 3b で、VLAN10 に書き直す。
- **決定（2026-11-10）: 今の LAN の DHCP が配る DNS は、ルーター（`192.168.11.1`）にする。** 段階 3 の間の今の LAN は、使う端末が少なく、一時的なネットワークなので、`vm-infra` が止まっても名前が引ける側に寄せる。ACL に「今の LAN → `vm-infra` の DNS(53)」を足さなくて済む。最終形の Management の緊急用プールも、ルーターを配る（[ADR-0027](0027-servers-octet-bands-and-emergency-dns.md)）。ER605 の DNS プロキシが、今の LAN で外部の名前を引けることは、2026-11-10 に確認した。内部の名前（`*.lab.kanare.dev`）は、今の LAN では引けない（IP で入る）。
- 段階 3 の前に決めること（未決）: `vm-infra` が止まったときの緊急用の入口（VLAN10 に端末を繋ぐ口がない間）、今の LAN の ACL。
- 段階 3b の前に決めること（未決）: 機器の接続先を直す手段、時期、順序。
- 機器の接続先を直す手段が見つかり、C-2 が解決したら、管理系を段階 3 に含める案を、再検討する（新しい ADR で置き換える）。
