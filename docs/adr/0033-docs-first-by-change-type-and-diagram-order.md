# 0033. 文書の更新は、変更の種類で「先」か「同時」かを分け、構成図は to-be を先に、as-is は実機の変更ごとに更新する

- ステータス: 採用
- 日付: 2026-11-20

## 背景

今の決まりは、「設定を変えたら、**同じ変更で**文書を更新する」だった。2026-11-20 の案 B（既定のネットワークの VLAN10 への統合。[ADR-0032](0032-merge-default-network-into-management-vlan10.md)）では、事前の手順書に、予測が外れた点が多かった（`Management` が消せない、スイッチから VLAN10 が消える、p2 のタグ付きに Management が要る、など）。実施のあとに、実績を書き足して直した。

また、Omada のように、**GUI でしか変えられない設定**は、変更の diff が残らず、レビューできる成果物が、文書しかない。

構成図は、to-be（目指す姿）と as-is（現状）の 2 枚を保っている。移行が段階的で、途中の状態が何日も続くことがある。

運用者が、「構成を変えるときは、文書を更新してから変える」「設計を変えるときは、to-be を更新して設計し、as-is は実機に合わせる」運用にしたいと考えた（2026-11-20）。

## 決定

1. **文書を、いつ更新するかは、変更の種類で分ける。**

   | 変更の種類 | 運用 | 理由 |
   | --- | --- | --- |
   | GUI でしか変えられない設定（Omada） | **文書が先** | 変更の diff が残らない。文書が、変更前に見直せる、唯一のチェックリスト |
   | 壊れると影響が大きい変更（VLAN、ACL、DNS、ルーター） | **文書が先** | 事前の予測が外れやすい。事前に書いて見直す価値が大きい |
   | コードで管理している設定（Terraform、Ansible、AdGuard の設定ファイル、Tailscale の ACL） | **同時**（同じ PR） | コードの diff が、すでにレビューの対象 |
   | 小さく、戻しやすい変更（DHCP の範囲、DNS レコード 1 件、ダッシュボード） | **同時** | 先に書く手間が、変更より重い |

   「文書が先」は、変更後の値を PR で書き、マージしてから、実機を変える。

2. **どの変更でも、実施のあとに行う。** 事前の文書は予測なので、**実機で確かめていない項目は「未確認」と明記**する。実施のあと「確認済み」にして、**予測が外れた点を同じ文書に書き**、変更履歴に 1 行足す。
3. **構成図**: 設計を変えるときは、**先に to-be を更新して設計する**（実機を変える前）。**as-is は、実機を変えたとき**（IP、VLAN、ポート、VM・サービス。図に出る変更だけ）に、実態に合わせて更新する。「to-be と一致したときだけ」にはしない。GUI だけで変える変更の as-is は、実機を変えたあとの PR で直し、コードで管理する変更は、同じ PR で直す。

## 理由

- 「必ず、すべて、文書が先」にすると、小さな変更で手間が重くなり、運用者が 1 人なので、守られなくなって、文書が古くなる。レビューの成果物が他に無い変更に、絞る。
- as-is を「to-be と一致したときだけ」更新すると、途中の状態（例: ADR-0032 の前の、ER605 が `10.77.1.1`（VLAN1）の期間）の図が、実機と違う状態になる。as-is と to-be の**差が、残りの作業**を表す、という使い方もできなくなる。

## 代替案

| 案 | 採らなかった理由 |
| --- | --- |
| すべて「同時」（今までの決まり） | GUI だけの変更と、影響の大きい変更で、事前に見直す機会が無い |
| すべて「文書が先」 | 小さな変更で手間が重い。守られなくなる |
| as-is を、to-be と一致したときだけ更新する | 途中の状態の as-is が、実機と違う。残りの作業が見えなくなる |

## 影響と再検討の条件
