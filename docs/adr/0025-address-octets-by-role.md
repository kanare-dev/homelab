# 0025. 第 4 オクテットは役割で決め直し、Management に緊急用の DHCP プールを置く

- ステータス: 採用（未適用。段階 3 で適用）
- 日付: 2026-11-05
- [ADR 0015](0015-vlan-address-scheme-10-77.md) の「ホストの末尾オクテットは現在の値を引き継ぐ」を置き換える。`10.77.<VLAN>.0/24` の体系と、第 3 オクテット = VLAN ID は変えない

## 背景

0015 は、覚え直す量を減らすため、各ホストの末尾オクテットを現行の値から引き継ぐと決めた。しかし、計画の中で既に崩れていた。

- `vm-omada`（`.12` → `10.77.10.3`）と Buffalo（`.2` → `10.77.30.10`）は、引き継げなかった。`.2–.9` が Management 専用なので、Buffalo は苦肉の策になった。
- 現行の番号は、導入順の経緯で決まったもの（`.12` が空き、`.20` 台が混在）で、番号から用途が分からない。
- 全ホストの IP が、どうせ一斉に変わる。引き継いでも、覚え直す負担はほぼ減らない。
- Management に DHCP が無いと、緊急時に Mac を直結するとき、固定 IP を手で振る必要がある。工場出荷時の機器の採用でも詰まる可能性がある（未確認）。

検討の経緯と選択肢: [IP 割り当てと DHCP の見直し](../operations/roadmap/12-ip-address-and-dhcp-review.md)

## 決定

1. 第 4 オクテットを、役割で決める。区切りは全 VLAN 共通。
   - `.1` ゲートウェイ、`.2–.9` ネットワーク機器（Management のみ）、`.10–.49` 固定、`.50–.99` DHCP 予約、`.100–.149` または `.100–.199` DHCP プール、`.200–.254` 予備。
   - ホストの割り当ては [VLAN 設計](../architecture/08-vlan-design.md#固定アドレス)の表のとおり。`vm-infra` は `10.77.20.10`、`vm-monitoring` は `.11`、`vm-apps` は `.12`、`vm-code` は `.13`、`vm-dev` は `10.77.40.10`、Buffalo は `10.77.30.50`。
2. DHCP が配る DNS は `10.77.20.10`（`vm-infra`）になる（[ADR 0024](0024-dhcp-dns-single-no-fallback.md) の判断は変わらず、アドレスだけ変わる）。
3. DHCP の範囲とリースを、VLAN ごとに決める。
   - Management: `.240–.250`（緊急用、リース 1 時間）。Trusted: `.100–.199`（24〜48 時間）。Lab と IoT: `.100–.149`（24 時間）。Guests: `.100–.199`（4 時間）。Servers・DMZ: なし。
4. Management の緊急用プールは、工場出荷時の機器が DHCP の無い VLAN でどう振る舞うかを確認して、問題なければ外す。

## 理由

- 末尾から用途が推測できる。例外が増える場当たりの採番を避けられる。
- 予約をプールの外（`.50–.99`）に置くので、予約とプールが衝突せず、Omada の予約の一覧が見やすい。
- 設計だけの今なら、書き換えは文書の置換で済む。適用してからだと、実機の設定変更まで増える。
- IoT と Lab は、台数に合った範囲に絞ると、異常に増えたとき（侵入、リースの枯渇）に気づきやすい。`/24` なので、足りなければすぐに広げられる。

## 代替案

| 案 | 判断 |
| --- | --- |
| A. 現行を引き継ぐ。`vm-omada` と Buffalo だけ例外 | 見送り。例外が既に 2 件。番号に意味が無いまま残る |
| C. 区切りは変えず、連番に詰めるだけ | 見送り。固定と予約を分ける実利が無く、手間は B と同じ程度 |
| Management に DHCP を置かず、Runbook で補う | 見送り。障害対応中の手順の見落としが怖い。実機で確認できたら、この案に戻す |

## 影響と再検討の条件

- 段階 3 まで、設計書に「現在」（`192.168.11.x`）と「移行後」の 2 つの値が並ぶ。段階 1・2 の IP と DHCP（`192.168.11.60–.99`）は変えない。
- 書き換えの対象: VLAN 設計、移行計画、構成図（`docs/diagrams/main-diagram/`）。段階 3 の前に、Ansible・Terraform・Caddy・Prometheus・Tailscale の IP を、新しい値で用意する。
- Management に、自動でアドレスを得られる口ができる。Management に出せるのは SG2210P の物理ポートだけなので、使わないポートは Management にしない。
- 実機の確認で、緊急用プールが不要と分かったら、新しい ADR で外す。

詳細: [VLAN 設計](../architecture/08-vlan-design.md)、[ER605・SG2210P の移行計画](../operations/roadmap/10-er605-sg2210p-migration-plan.md)
