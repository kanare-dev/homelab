# 0018. 回線速度は speedtest-exporter で測り、通知は 7 日間の中央値との比較にする

- ステータス: 採用（未適用）
- 日付: 2026-11-01

## 背景

家のインターネット回線の速度を監視し、推移を見られるようにして、遅くなったら通知したい。
既存の監視（[監視・アラート](../services/03-monitoring.md)）は、VM・ストレージ・HTTPS・DNS が対象で、回線の速度は見ていない。外形監視（blackbox）は LAN 内のサービスと、AdGuard 経由の名前解決だけで、回線の品質（速度・遅延）は分からない。

## 決定

- `vm-monitoring` に `speedtest-exporter`（Ookla Speedtest CLI を Prometheus 形式で出す）を置く。Prometheus が 1 時間毎に scrape し、scrape のたびに 1 回測る。
- 推移は Grafana「Internet Speed」で見る。通知は既存の Alertmanager から Slack へ送る。
- 「遅い」の基準は固定の数値ではなく、**直近 7 日間の中央値の 60%**。直近 3 時間の最大値がそれを下回ったら通知する。測定が 48 回（約 2 日）溜まるまでは評価しない。
- 測定の失敗（`SpeedtestFailing`）は 3 時間続いたら通知する。
- 対象はまずインターネット回線のみ。家庭内 LAN は iperf3 で同じ仕組みに足せる設計にして、手順を文書に残す（[家庭内 LAN への拡張](../services/03-monitoring.md#家庭内-lan-への拡張未実装)）。

## 理由

- 既存の Prometheus・Grafana・Alertmanager にそのまま載る。新しい DB や通知経路を作らない。
- 中央値との比較なら、契約速度を調べて数字を決めなくてよい。回線を替えても追随する。一度の外れ値や夜間の混雑では通知しない。
- ポートを公開しない（Prometheus からだけ使う）。ポート開放が要らない。

## 代替案

| 案 | 見送った理由 |
| --- | --- |
| MySpeed | 独自の DB と画面を持ち、Prometheus・Alertmanager に載らない。通知経路と画面が増える |
| LibreSpeed | 自分で立てたサーバーまでの速度を測るので、インターネット回線の速度にならない（LAN 内の測定向き） |
| 固定のしきい値 | 契約速度や実測の平常値を先に決める必要がある。回線を替えるたびに直す |
| iperf3（回線） | 測定の相手が外部に要る。回線ではなく LAN の測定向き |

## 影響と再検討の条件

- 測定のたびに回線を使う。通信量は回線速度に比例する（Ookla は速度に応じて転送量が増える。1Gbps 級なら 1 回で 1〜2GB 前後、1 日 24 回で数十 GB になりうる）。従量課金や、使用量の上限がある回線では、間隔を延ばす（`prometheus.yml` の `scrape_interval`）。
- 通知までの遅れは最大で約 3 時間。速い検知が目的ではなく、劣化の傾向を捉える設計。回線断の検知は、外部 Heartbeat と `SpeedtestFailing` に任せる。
- `vm-monitoring` 経由で測るので、同じ VM や LAN の大きな通信と重なると遅く出る。ルーター（Buffalo）直下の値ではない。
- 外れ値による誤報が多い、または見逃しが多い場合は、`0.6` と `[3h]` を調整する。
- 外部サービス（Ookla の測定サーバー）に依存する。CLI の提供条件が変わったら再検討する。
- LAN の速度監視を始めるとき（VLAN 化の前後比較など）は、iperf3 の手順に従って足す。
