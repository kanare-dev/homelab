# 段階 3b の作業（管理系を VLAN10 へ移す。機器を先に動かす）

**状態: 草案（未実施）。** 2026-11-18 の 2 回の試験（[ロードマップ 13](../roadmap/13-defer-management-vlan.md)）で、「機器が旧 LAN にいる間に、コントローラーの住所だけを動かす」方式は成功しなかった。そこで、運用者の依頼（2026-11-18）で、**案 1（機器を先に VLAN10 へ移し、そのあとコントローラーを移す）**を手順にした。この方式を採用するかは、まだ決めていない。採用するときは、同じ変更で、[ADR](../../adr/README.md) と[VLAN 設計](../../architecture/08-vlan-design.md)に移す（CLAUDE.md の「検討と採用」）。

段階 3（[当日の作業](21-network-cutover-stage-3.md)）が済んでいることが前提。管理系（SG2210P、ER605、`vm-omada`）を、今の LAN（`192.168.11.0/24`）から Management（VLAN10、`10.77.10.0/24`）へ移す。Proxmox ホストの移動（`vmbr0.10`）は、この手順書に含めない（物理コンソールが要る別の作業。下の「このあとの作業」）。

- 秘密の値と、機器の MAC アドレスは書かない（台帳へ）。
- 作業時間の見込み: 2〜3 時間（予備を含む）。**途中で判断の分かれ道がある。時間に余裕のある日に行う。**
- 各手順に「確認」と「戻し方」を付けた。**確認が通るまで、次へ進まない。**

## 考え方（なぜ、この順序か）

2 回の試験で分かったこと:

- 機器には、新しい住所は**伝わる**（機器が `10.77.10.3` に接続を試した）。ただし、接続は完了しなかった。
- `vm-omada` が NIC を 2 枚持つ（`eth0` が旧 LAN、`eth1` が VLAN10）と、**機器が旧 LAN から VLAN10 のアドレスへ来た接続の返事が、`eth0` から出る**（非対称ルーティング）。ER605 には、異常な通信に見える。
- 経路を直しても付いてこなかったので、原因は、これだけではない可能性がある（未確認）。

そこで、**機器を先に VLAN10 へ移し**、機器とコントローラーを同じネットワーク（`10.77.10.0/24`）に置く。同じネットワークなら、返事は、同じ NIC から、ルーターを通らずに出る。コントローラーの NIC が 1 枚（VLAN10 だけ）の最終形でも、機器とは同じ経路になる。

**未確認のこと（実施の前に知っておく）:**

- SG2210P の管理 VLAN と IP を、コントローラーの画面から変えたとき、機器が切れずに付いてくるか。
- ER605 は、コントローラーへの接続の送信元を、旧 LAN の自分の住所（`192.168.11.1`）にするようだ（2026-11-18 のキャプチャ）。これが、VLAN10 のコントローラーへの接続で、問題になるか。
- 「デバイス管理アクセス」で、機器が付いてくるか（2 回の試験は、成功していない）。

## 0. 前提の確認と準備

- [ ] 段階 3 が済み、ACL が**全許可**のまま（VLAN10 と旧 LAN の間も通る）。ACL を絞った後なら、VLAN10 ↔ 旧 LAN、VLAN10 ↔ `vm-omada` の通信（29810/udp、29811〜29816/tcp、8043/tcp）を許可してから始める。
- [ ] `vm-omada` が、2 枚の NIC を持つ（`eth0` が `192.168.11.12`、`eth1` が `10.77.10.3`）。UFW に、機器向けの 3 ルールの許可元として `10.77.10.0/24` が入っている（2026-11-18 に済み。PR #13）。
- [ ] **Omada のバックアップを取る**（設定 → メンテナンス → バックアップ。iCloud Drive の `homelab/` に、日付を付けて保存）。**SG2210P と ER605 の設定の変更前の状態**を持つため。
- [ ] 戻し方（下記）を読んだ。
- [ ] **物理コンソール**（キーボードとモニター）を、Proxmox にすぐ繋げられる。Mac に、**有線の口**（SG2210P の p6、緊急用の入口。native VLAN1）と、固定 IP `192.168.11.x` を振る手段がある。
- [ ] 作業中にインターネットが要るとき用に、スマホ（モバイル回線）がある。
- [ ] 作業中に出るアラート（`TargetDown`、`GatewayUnreachable`、`Watchdog`、Heartbeat）は、想定内。
- [ ] SG2210P の IP を、静的にする計画を決める（`10.77.10.2/24`、ゲートウェイ `10.77.10.1`、DNS `10.77.10.1`）。**DHCP のままにしない**（公式の FAQ は、静的 IP の事前設定を勧める）。
- [ ] 「デバイス管理アクセス」が、**オン**で、`192.168.11.12` になっている（グローバルビュー > 設定 > システム設定 > デバイス管理アクセス）。

## 1. SG2210P の管理 VLAN と IP を、VLAN10 に変える

**これで、SG2210P だけが `10.77.10.2` に移る。コントローラー（`192.168.11.12`）は、動かさない。** SG2210P は、ER605 を通って、旧 LAN のコントローラーへ接続する。データの通信（ポートの VLAN）には影響しない（管理用の口の話）。

1. Omada の画面で、`sg2210p` の設定を開く。管理 VLAN を VLAN10（Management）にし、IP を静的（`10.77.10.2/24`、GW `10.77.10.1`、DNS `10.77.10.1`）にする。（**画面の場所は、当日確認する。** 未確認。）
2. 適用する。SG2210P が、再接続のために、一度切れることがある。5 分待つ。

**確認:**

- [ ] Omada の画面で、`sg2210p` が「接続済み」に戻り、IP が `10.77.10.2` になっている。
- [ ] `vm-omada` で `sudo ss -tn state established '( sport >= :29811 and sport <= :29816 )'` を実行すると、`10.77.10.2` からの接続が見える。
- [ ] Proxmox、`vm-omada`、Mac（p4）、Wi-Fi の端末の疎通が変わらない（SG2210P はスイッチなので、データは変わらないはず）。

**戻し方:**

- 画面から戻せるとき: 管理 VLAN を VLAN1、IP を DHCP に戻す。
- 戻せない（切れたまま）とき: 緊急用の p6（native VLAN1）に Mac を繋ぎ、SG2210P のローカルの画面か、リセット（本体のボタン）で復旧する。バックアップ（手順 0）から、設定を戻す。再採用が要る（段階 1・2 と同じ作業）。**SG2210P が切れても、すでに設定されたポートの VLAN は、動き続ける**（見込み。未確認）。

## 2. 「デバイス管理アクセス」を `10.77.10.3` にして、SG2210P が付いてくるか確かめる

SG2210P は、コントローラーと同じネットワークにいる（`10.77.10.2` と `10.77.10.3`）。非対称ルーティングの影響を受けない、最初の確認。

1. 「デバイス管理ホスト名/IP」を `10.77.10.3` にして、適用する。
2. コントローラーのコンテナを再起動する（`docker restart omada`。画面と管理が 1〜2 分止まる。通信は止まらない）。再起動しないと、つなぎっぱなしの接続は変わらない（2026-11-18 に確認）。
3. 機器の再接続を、次のコマンドで見る。

   ```bash
   ssh vm-omada 'sudo ss -tn state established "( sport >= :29811 and sport <= :29816 )"'
   ```

**確認:**

- [ ] SG2210P（`10.77.10.2`）が、**`10.77.10.3`（`[::ffff:10.77.10.3]`）宛て**に接続している。
- [ ] ER605 は、旧住所のままでもよい（次の手順で扱う）。

**判断:**

- SG2210P が `10.77.10.3` に付いてきた → 手順 3 へ。
- 付いてこない（5 分待っても、`10.77.10.3` 宛の接続が出ない）→ **ここで止める。** 値を `192.168.11.12` に戻す。「デバイス管理アクセス」が効かないことが確定する。案 3（機器のリセットと再採用）へ進む（下の「別の道」）。

**戻し方:** 「デバイス管理ホスト名/IP」を `192.168.11.12` に戻して、適用し、コンテナを再起動する。SG2210P は、旧住所に戻る（2026-11-18 に、ER605 と SG2210P が、旧住所に戻ることを確認した）。

## 3. ER605 が付いてくるか確かめる

ER605 は、**旧 LAN の自分の住所（`192.168.11.1`）を送信元にして、VLAN10 のコントローラーに来る**（2026-11-18 の観測）。`vm-omada` が 2 枚の NIC を持つ間、返事が `eth0` から出る問題がある。

1. `vm-omada` に、返事の経路を直す設定（policy routing）を、**一時的に**入れる（再起動で消える）。

   ```bash
   sudo ip route add default via 10.77.10.1 dev eth1 table 100
   sudo ip rule add from 10.77.10.3 lookup 100 priority 100
   ```

2. 手順 2 のあと、ER605 が付いてきたかを、`ss` で見る。付いてこなければ、コンテナを再起動して、5 分待つ。

**確認:**

- [ ] ER605 が、`10.77.10.3` 宛て（`[::ffff:10.77.10.3]`）に接続している。Omada の画面で「接続済み」。

**判断:**

- 付いてきた → 手順 4 へ。
- 付いてこない → **ER605 だけ、再採用を検討する**（下の「別の道」）。SG2210P は、新しい住所で動いている。ER605 の再採用は、インターネットが止まる作業（段階 1・2 で行った。バックアップあり）なので、日を改めてもよい。

**戻し方:** `sudo ip rule del from 10.77.10.3 lookup 100; sudo ip route flush table 100`。

## 4. `vm-omada` を VLAN10 の 1 枚にする

機器が両方とも `10.77.10.3` に付いてきたあと、旧 NIC を外す。

1. Terraform（`terraform/proxmox/terraform.tfvars` の `vm-omada`）: `ip = "10.77.10.3/24"`、`gateway = "10.77.10.1"`、`nameserver = "10.77.10.1"`、`vlan_id = 10`。`extra_nic` を消す。`terraform plan` で、`vm-omada` だけが in-place 更新であることを確かめて、`apply`（VM が再起動する。[apply による再起動](15-terraform-apply-restart.md)）。
2. Ansible の `inventory/hosts.yml`（`ansible_host`）を `10.77.10.3` に。`group_vars/omada/vars.yml` の UFW から、`192.168.11.0/24` の 3 行と、policy routing 用の注記を消し、`ufw_removed_ports` に、旧ルールを足す。`ansible-playbook playbooks/site.yml --limit vm-omada` を流す。SSH のホスト鍵が変わったら、`known_hosts` を更新する（cloud-init の再実行による。2026-11-18 に経験した）。
3. 参照先を直す: Caddy の `omada.lab.kanare.dev`（`docker/compose/reverse-proxy/Caddyfile` の `reverse_proxy https://10.77.10.3:8043`）、Prometheus の `vm-omada` の targets（`docker/compose/monitoring/prometheus/prometheus.yml`）、`~/.ssh/config`。`vm-infra` と `vm-monitoring` に、Ansible と Compose で反映する。
4. 設計書を直す（IP 一覧、構成図 as-is、各機器の設定書の変更履歴）。

**確認:**

- [ ] `omada.lab.kanare.dev` が開く。Omada で、ER605・SG2210P が「接続済み」。
- [ ] Prometheus で、`vm-omada` が `up`。
- [ ] コンテナを再起動して、機器が `10.77.10.3` に戻ってくる（5 分以内）。

**戻し方:** Terraform を、旧い値（`192.168.11.12`、タグなし）に戻して `apply` する。機器は、「デバイス管理アクセス」を `192.168.11.12` に戻せば、旧住所に付いてくる（2026-11-18 に確認）。

## 5. ER605 の管理 IP（任意）

ER605 は、VLAN10 のゲートウェイ（`10.77.10.1`）を、すでに持つ。ER605 自身の管理 IP は、LAN の `192.168.11.1`（既定の VLAN1）のままでもよい。既定の LAN を `10.77.1.0/24` にする作業（[ロードマップ 13](../roadmap/13-defer-management-vlan.md#既定の-lan-のアドレス検討中)）は、別の作業。

## 別の道（手順 2・3 が通らないとき）

- **機器のリセットと再採用**（案 3）: バックアップを取り、機器を初期化して、コントローラー（`10.77.10.3`）で採用し直し、バックアップから設定を戻す。段階 1・2 と同じ作業。ER605 の再採用は、インターネットが止まる。時間を選ぶ。
- **採用済みの機器に、住所を直接書き換える手段を探す**（案 2）。未調査。

## このあとの作業（この手順書の外）

- Proxmox ホストを `vmbr0.10`（`10.77.10.10`）へ移す（物理コンソールが要る）。
- 既定の LAN（VLAN1）を `10.77.1.0/24` に変える、または廃止する。
- ACL を絞る（[ADR-0029](../../adr/0029-stage3-acl-allow-all-then-tighten.md)）。
- 段階 3b の完了後に、as-is の構成図（`docs/diagrams/as-is-diagram/`）を削除する。
