## 要約

2026-09-09 18:49、Proxmox の LVM-thin プールが満杯になり、全 6 VM が `io-error` で一時停止した。
通知の仕組みが存在せず、利用者が 10/22 に DNS の不調で気づくまで **約 42 日間** 誰も気づかなかった。

復旧そのものは数分で済んだ。VG に未割当が 16 GiB 残っていたため、pool を 14 GiB 拡張して `qm resume` するだけで全 VM が戻った。

調べると、ゲスト内の実データは 5 VM 合計で約 28 GiB なのに、pool への割当は約 97 GiB あった。
**全ディスクで `discard` が無効**だったため、ゲストが書いて消したブロックが pool に返らず、割当だけが増え続けていた。
有効化して `fstrim` をかけると、pool 使用率は 100% から 38% まで下がった。

最大の損失は復旧の遅さではなく、**検知の遅れ**だった。再発防止として、thin pool と VM 状態の監視、14 件のアラート、Slack 通知、
容量上限（ログ、journald、Prometheus）、Grafana ダッシュボードを導入した。VM を実際に止めて、約 4 分で Slack に通知が届くことを確認している。

## 2. 調査結果（2026-10-22 14:54 時点・読み取りのみ）

### 2.1 thin pool

```text
data              141.60g  Data% 100.00  Meta% 4.28   (twi-aotzD-)
```

- **Data% が 100%、Metadata% は 4.28%**。枯渇したのはデータ領域で、メタデータではない。
- VG `pve` は 237.47 GiB で、**未割当（VFree）が 16.00 GiB** あった。pool を拡張できる余地があった。
- 物理ディスク（`nvme0n1`）の SMART は PASSED。ハード故障ではない。
- `local`（dir）は 24% で余裕があった。

### 2.2 ディスクごとの割当

| VMID | 名前 | 仮想サイズ | Data% | 実割当（概算） |
|---|---|---:|---:|---:|
| 111 | vm-infra | 20 GiB | 92.21% | 18.4 GiB |
| 113 | vm-monitoring | 40 GiB | 90.36% | 36.1 GiB |
| 130 | vm-windows | 60 GiB | 60.00% | 36.0 GiB |
| 121 | vm-dev | 30 GiB | 59.50% | 17.9 GiB |
| 120 | vm-apps | 40 GiB | 41.29% | 16.5 GiB |
| 122 | vm-code | 30 GiB | 49.54% | 14.9 GiB |
| 9000 | ubuntu-cloud（テンプレート） | 3.5 GiB | 50.91% | 1.8 GiB |
| | **合計** | **223.5 GiB** | | **≈141.6 GiB** |

仮想ディスクの合計（223.5 GiB）が pool（141.6 GiB）の約 **1.6 倍**。各 VM が自分のディスクを使い切る方向に進めば、必ず pool が先に枯渇する構成だった。

### 2.3 設定の問題

- **全 VM ディスクに `discard=on` が設定されていない**（`qm config`）。ゲストが削除しても、pool の割当は戻らない。
- **スナップショットは存在しない**。スナップショット起因の消費という仮説は否定できた。
- **vzdump のバックアップとジョブはない**。
- Terraform のディスク定義にも discard の指定がなかった（IaC に起因して欠けていた）。
- LVM の `thin_pool_autoextend_threshold` は未設定で、自動拡張も効かない。

### 2.4 障害時点の監視の状態

- Prometheus に **`rule_files` も `alerting` もなかった**。Alertmanager も未導入で、**アラートが 1 つも存在しなかった**。
  当初「アラートが機能していなかった」と想定していたが、実際は「無かった」。
- 標準の node_exporter は **LVM thin pool の使用率を出さない**。pve の `/` や `local` の使用率は見えても、今回枯渇した領域は監視対象外だった。
- `vm-code` と `vm-windows` は scrape 対象に入っていなかった。
- Prometheus は `retention.time=30d` のみ。Docker のログ上限は、どの compose にもなかった。

## 3. 原因分析

### 3.1 直接原因（確定）

thin pool `pve/data` の Data% が 100% に到達した。VM の書き込みが失敗し、QEMU が 6 VM を `io-error` で一時停止した。

### 3.2 発生時刻の特定（3 つの独立した証拠）

当初、発生時刻は不明だった。初回調査でカーネルログの範囲を直近 1 週間にしたため「記録なし」と判断し、
誤って「約 104 日かけて蓄積」と推定していた。次の 3 点を突き合わせて、9/9 であることを確定した。

| 証拠 | 内容 |
|---|---|
| PVE のカーネルログ | `2026-09-09 18:49:21 ... switching pool to out-of-data-space`、`18:50:24 ... (error IO) mode`、`2026-10-22 14:56:46 ... switching pool to write mode` |
| Prometheus のデータ | 永続化された最後のブロックは 9/9 19:00〜21:00。それ以降のメトリクスは存在しない |
| ゲストの稼働時間 | 5 台とも、PVE から見たプロセス稼働時間より **約 42.8 日短い**。vm-monitoring のカーネルログにも `Long readout interval ... cs_nsec: 3697033686022505`（≈42.79 日）が記録されている |

ゲストは一時停止中は時間が進まない。そのため、3 つ目の証拠は「9/9 から全 VM が止まっていた」ことを独立に裏付ける。

### 3.5 復旧後の調査: 実データと割当の乖離

| VM | ゲスト内 `/` の使用量 | pool 上の割当 | 差（回収可能の目安） |
|---|---:|---:|---:|
| vm-infra | 8.8 GiB | 18.4 GiB | ≈ 9.6 GiB |
| vm-monitoring | 5.5 GiB | 36.1 GiB | ≈ 30.6 GiB |
| vm-apps | 3.9 GiB | 16.5 GiB | ≈ 12.6 GiB |
| vm-dev | 4.1 GiB | 17.9 GiB | ≈ 13.8 GiB |
| vm-code | 5.6 GiB | 14.9 GiB | ≈ 9.3 GiB |
| vm-windows | 34 GiB | 35 GiB | ≈ 1 GiB |

- ゲストの実データは 5 VM 合計で **約 28 GiB**。pool への割当は **約 97 GiB**。差の約 76 GiB は、「一度書かれ、削除されたが discard されず pool に残ったブロック」と推定される。
- 各ゲストの `/` は `rw` で、`dmesg` に I/O エラーも FS の再マウントもなかった。FS の破損は確認されていない。
- Prometheus は再開時に `out of sequence m-mapped chunk` を出し、head のチャンクを破棄した。9/9 の停止直前の数時間分は欠落した可能性がある。永続化済みブロック（〜9/9 19:00）は健全。

**割当が増えた有力候補: AdGuard Home のクエリログ**（推定）

| ファイル | サイズ | 更新日時（ゲスト時計） |
|---|---:|---|
| `querylog.json.1` | **約 1.2 GB** | 2026-09-09 19:15 |
| `querylog.json` | 約 0.5 MB | 10-22（復旧後） |

- 設定は `querylog.interval: 2160h`（90 日保持）。ローテーションで GB 単位のファイルを書き換えると、旧ブロックは discard されず pool に残る。
- 保持を 7 日にして AdGuard を再起動すると、`querylog.json.1` は 1.2 GB → 約 0.77 MB に縮んだ。
- ただし、この 1 件で 76 GiB は説明できない。他にも、apt やイメージの更新、ログの書き換えなどが寄与したと考えられる（未検証）。

## 4. 対応

### 4.1 暫定対応（復旧）

VM 内のデータは削除していない。強制停止やリセットも行わなかった。

1. **pool を拡張**: `lvextend -L +14G pve/data`（VG の未割当 16 GiB のうち 14 GiB。メタデータ用の余裕を残した）。
2. **VM を再開**: `qm resume` を、DNS の vm-infra → 113 → 120 → 122 → 121 → 130 の順に実行。
3. **容量の回収**: 全 VM に `discard=on,ssd=1` を設定し、VM を 1 台ずつ再起動して `fstrim -av`。vm-infra（DNS）は最後に実施。

結果は、pool 100% → 91%（拡張）→ 約 44%（discard + fstrim）→ 現在 38%。

### 5.3 根本原因（5 Whys）

1. **なぜ全サービスが止まったか** → thin pool が満杯になり、VM ディスクへの書き込みが失敗して、QEMU が VM を停止したから。
2. **なぜ pool が満杯になったか** → ゲストが書いて消したブロックが pool に返らず、割当だけが増え続けた（実データ約 28 GiB に対し割当約 97 GiB）から。
   さらに、仮想ディスクの合計（223.5 GiB）が pool（141.6 GiB）の約 1.6 倍で、先に pool が尽きる構成だった。
3. **なぜ返らなかったか** → 全 VM ディスクに `discard=on` を設定しておらず、ゲストの TRIM が pool に届かなかったから。
4. **なぜ気づけなかったか** → pool の使用率を測るメトリクスもアラートもなく、Alertmanager も未導入だったから。監視基盤自身も同じ pool 上にあり、障害時に止まる構成だった。
5. **なぜ設計時に防げなかったか** → VM を作る時点で「容量は使用量だけで決まる」と想定し、thin provisioning 固有のリスク（返却されない割当、過剰割当）を設計のチェック項目に含めていなかったから。

**未解決**: 約 76 GiB の割当が、具体的に何の書き込みで増えたかは特定できていない（AdGuard のクエリログが有力候補）。
Grafana の「VM ディスクごとの増加ペース」で、discard 有効後の増え方を観察する。

### 5.4 うまくいったこと / いかなかったこと / 幸運だったこと

**うまくいったこと**

- Terraform / Ansible / ドキュメントが揃っており、構成の把握と再現が早かった。
- PVE への SSH が生きており、読み取り専用の調査から始められた。
- 強制リセットをせず、`qm resume` で再開した。ゲストの FS を壊さずに復旧できた。
- VG に未割当が 16 GiB 残っており、データを消さずに pool を拡張できた。
- 復旧後にゲスト内の実使用量を調べ、原因が「データの増加」ではなく「割当が返らないこと」だと特定できた。
- 検知の仕組みを作ったあと、実際に VM を止めて通知が届くことを確認した。

**うまくいかなかったこと**

- 検知手段がなく、42 日間気づけなかった。
- バックアップがなく、FS が壊れていた場合に戻せなかった。
- 初回調査で、カーネルログの検索範囲を狭く取り、「記録なし」「約 104 日で蓄積」と誤って推定した。3 つの証拠を突き合わせて訂正した。
- 暫定対応（pool の拡張）だけでは 91% にとどまった。容量の回収には、discard を反映するための VM 再起動が必要で、1 台あたり 1〜2 分の計画停止が発生した。
- 収集スクリプトにボリューム別メトリクスを追加した際、非アクティブなテンプレートボリュームの空値が原因で、約 6 分間 PVE のメトリクスが途絶えた（node_exporter は不正な行があるとファイル全体を読まない）。アラートの待ち時間内に収まり、通知は出なかった。変更時の確認手順を `docs/services/monitoring.md` に追記した。
- Windows の ACPI シャットダウンが遅く、再起動の作業が一時止まった。

**幸運だったこと**

- pool が `error IO` モードに入り、QEMU が VM を停止した。ゲスト内で FS エラーが多発して破損する前に止まった。
- 42 日の停止中に、Let's Encrypt の証明書が失効しなかった（9/6 発行、12/5 期限）。
- 物理ディスクに故障がなかった（SMART PASSED）。

### 5.5 教訓

1. 利用者から見える症状（DNS の不達）と原因（基盤ストレージの枯渇）は、別の階層にあった。症状の階層ではなく、下位から調べる。
2. thin provisioning では「ゲスト内の使用率」と「pool の使用率」は別物。pool を直接監視しなければ気づけない。
3. discard が無いと、thin pool の割当は減らない。オーバープロビジョニングと組み合わさると、枯渇は時間の問題になる。
4. 「アラートが機能していなかった」と思い込んでいたが、実際は **そもそも存在しなかった**。仮説を前提にせず、設定を確認する。
5. 監視基盤が障害対象と同じ基盤にあると、障害時に通知も止まる。完全には解消できない場合は、受容するリスクとして明記する。
6. **検知までの時間が最大の損失だった**。復旧操作は数分で終わったが、気づくまでに 42 日かかった。
7. **ログは期間を広く取って調べる**。直近だけを見て「記録なし」と判断し、発生時刻を誤った。複数の独立した証拠（カーネルログ、メトリクスの途切れ、ゲストの稼働時間）を突き合わせると確度が上がる。
8. **検知の仕組みは、実際に壊して確認する**。ルールを書いただけでは足りず、VM を止めて Slack に届くまでを確認した。
9. **モニタリング自体の変更も壊れる**。収集スクリプトの変更で自らメトリクスを止めた。変更手順（一時ディレクトリでの出力確認）を決めておく。
10. 公開リポジトリには、シークレットの値だけでなく、文字数やハッシュなど手がかりになる情報も書かない。

## 6. 記事化のためのメモ

記事にする場合の見どころと、使える材料。

**物語の軸**: 「復旧は数分、検知は 42 日」。障害そのものより、**気づく仕組みが無かったこと**が本題。

| 見どころ | 材料 |
|---|---|
| 症状と原因の階層のずれ | iPhone で `home.lab.kanare.dev` が開けない → DNS → VM の `io-error` → thin pool 100% |
| thin provisioning の落とし穴 | 実データ 28 GiB に対し割当 97 GiB。discard が無いと、削除しても返らない |
| 日付の特定 | 3 つの独立した証拠（PVE カーネルログ、Prometheus のデータの途切れ、ゲストの稼働時間のずれ 42.8 日）が一致した |
| 初動の誤り | 直近 1 週間だけを見て「記録なし」と判断し、「104 日で蓄積」と誤って推定した。広く調べて訂正した |
| 「アラートが壊れていた」のではなく「無かった」 | 設定を確認する前に仮説を置いていた |
| 実機テスト | VM を止め、約 4 分で `TargetDown` と `PveVmStopped` が Slack に届いた |
| 自分で起こした小さな障害 | 監視用スクリプトの変更で、メトリクスが約 6 分止まった（空値 1 行が原因） |
| 公開リポジトリでの線引き | シークレットの桁数やハッシュも書かない。台帳は非公開（iCloud Drive）にした |

**数字で語れる材料**: 停止 約 42 日 20 時間／検知 約 42 日 6 時間／復旧操作 約 4 分／pool 100% → 38%／回収した容量 約 83 GiB（pool 使用量 約 142 → 約 59 GiB）／AdGuard のクエリログ 1.2 GB → 0.77 MB／アラート 14 ルール。

**図にできるもの**: 症状から原因までの階層図、pool の使用率の推移（Grafana「Storage / Thin Pool」）、VM ディスクごとの割当とゲスト使用量の比較、通知経路（PVE → node_exporter → Prometheus → Alertmanager → Slack）。
