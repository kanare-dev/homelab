## 要約

段階 3 のリハーサルとして、Omada に Management（VLAN10）のネットワークを作った直後から、`vm-infra`（DNS）、`vm-omada`、Proxmox に、LAN から届かなくなった。ER605 とインターネット（IP）には、届いた。Heartbeat が途絶し、Omada Cloud はオフラインになった。

前回の障害（[INC-2026-10-25](2026-10-25-nic-hardware-unit-hang.md)）と症状が似ていたが、**NIC の送信停止ではなかった**（`Hardware Unit Hang` なし、リンクの上下なし）。原因は、**SG2210P の p2 の VLAN 設定が、ネットワークの作成のウィザードで書き換わったこと**だった。コントローラー（`vm-omada`）は、Proxmox の上にあるので、**止まった Proxmox を、コントローラーから直せない**循環があり、復旧が遅れた。

## 2. 調査結果

### 2.1 切り分け

| 確認 | 結果 | 分かったこと |
| --- | --- | --- |
| Mac から ER605（`.1`）、`1.1.1.1` | 届く | ルーターと回線は生きている |
| Mac から `.10`、`.11`、`.12` | 届かない（`host is down`） | Proxmox の側の L2 に届いていない |
| `dmesg`、`journalctl -k \| grep nic0` | `Hardware Unit Hang` なし。最後のリンクの上下は 11/07 17:40 | **NIC の送信停止ではない**（前回と違う） |
| `ethtool nic0` | `Link detected: yes` | リンクは生きている |
| ホストから `ping 192.168.11.1` | `Destination Host Unreachable`（ARP が解決しない） | Proxmox から先の L2 が、ER605 に届いていない |
| ER605 の WAN/LAN3 に挿し替え | 届く | **SG2210P の p2 の側が原因**（Proxmox の NIC・設定・VM は正常） |

### 2.2 根本原因（SG2210P の p2）

コントローラー（IP で開いた）で、p2 の VLAN Configuration を見た。

| 項目 | 障害中の値 | 本来の値 |
| --- | --- | --- |
| Native Network | **Management(10)** | Default(1) |
| Network Tags Setting | **Block All** | Allow All |
| Untagged Network | **Management(10)** | Default(1) |

- Proxmox は、**タグなし**で通信する。p2 の Native が Management(10) になったため、通信が VLAN10 に入り、既定の LAN（VLAN1。`192.168.11.1` がいる）に届かなくなった。ARP が解決できなかった理由。
- **確認済み（運用者の記憶）**: Management を作るウィザードの「Select Device Port」（手順 2）で、**p2 に VLAN10 のタグ付きの通信を通すつもりで、p2 を選んだ**。次の手順に進むと、すぐに接続が切れ、Heartbeat も途絶えた。ウィザードの設定結果（Native が作るネットワーク、タグは Block All）と、p2 の値が一致する。当時の画面そのものは、記録していない。
- **同じ操作が、ポートの種類で逆の結果になった**: リハーサルで VLAN30・VLAN50 を作ったときも、運用者は、ウィザードの手順 2 で **p5・p6 を選んだ**（それぞれ Native = Trusted(30)、IoT(50)、Block All）。p5・p6 は、その VLAN の端末を直接繋ぐ**アクセスポート**で、これは意図どおりの設定（リハーサルの A-2）だった。同じ流れで VLAN10 を作るときに、**トランクの p2**（Proxmox。タグなしの VLAN1 と、タグ付きの複数の VLAN を通す）を選んだため、逆効果になった。「VLAN を作ったら、そのポートを選ぶ」という、リハーサルの経験が、そのまま当てはまる、自然な操作だった。
- **意図と結果の食い違い**: 運用者の意図は、「p2 に VLAN10 を**タグ付きで**通す」だった。ウィザードの「ポートを選ぶ」は、**タグなし（Native）として所属させ、タグ付きを Block All にする**操作だった。画面に、その説明はない。
- ER605 の LAN ポートは、変わっていなかった（Native は Default のまま）。

### 2.3 なぜ復旧が遅れたか

- **循環**: コントローラー（`vm-omada`）は、Proxmox の上にある。Proxmox が LAN から消えると、コントローラーも消え、**p2 の設定を、コントローラーの画面から直せない**。
- 当初は、前回の障害（NIC の送信停止）と症状が似ていたため、NIC を疑った。コンソールの確認（モニターとキーボード）が、翌日になった。
- 夜間で、運用者が休んだ（人的な事情。仕組みの問題ではない）。

### 2.4 なぜ Slack に何も届かなかったか

- 監視と通知は、`vm-monitoring` の上にある。Proxmox が LAN から消えると、Alertmanager も外に出られない。
- [INC-2026-10-25](2026-10-25-nic-hardware-unit-hang.md) と同じ構造（[ADR-0002](../../adr/0002-no-external-monitoring.md) で受け入れたリスク）。**外部の Heartbeat（Healthchecks.io）が、途絶を検知して、メールで通知した**（設計どおり）。

### 2.5 DNS の UDP の件（自然に解消）

復旧の直後に、Mac から `@192.168.11.11` への問い合わせで、**TCP は答えるが、UDP はタイムアウト**する名前（`api.anthropic.com`）があった。`vm-infra` の中の Unbound は、直接問い合わせると正常で、外向きの DNS も通っていた。Unbound のログには、障害中（16:57）の `SERVFAIL`（ルートへの到達の失敗）だけが残っていた。

その後、p2 を直し、Proxmox を p2 に戻して、17:32 に再確認したところ、**UDP でも 3 ms で正常に答えた**。障害中の状態（キャッシュ、AdGuard の上流の状態など）の名残で、**一時的な問題**だったと見ている。原因は**未確認**（再発したら、`docker logs adguard`、AdGuard のレート制限、UFW を調べる）。

## 3. 復旧

1. Proxmox のケーブルを、ER605 の LAN ポート（WAN/LAN3）に、仮に挿し替えた（SG2210P を迂回）。`vm-omada` が戻った。
2. コントローラーに、IP で入り、SG2210P の p2 を直した（Native = Default(1)、Network Tags = Allow All）。
3. SG2210P の p1・p3・p4、ER605 の WAN/LAN2〜LAN5 が、変わっていないことを確認した。
4. Proxmox のケーブルを、p2 に戻した。`.1`、`.10`、`.11`、`.12` に届くことを確認した。

## 4. 恒久対応

## 6. ポストモーテム

- **うまくいったこと**: 外部の Heartbeat が、監視 VM の途絶を検知した（INC-2026-10-25 の対策が、機能した）。`Hardware Unit Hang` の有無と、リンクの上下の記録で、前回の障害と、早く切り分けられた。ER605 への直結の切り戻し（Runbook にあった手順）が、効いた。
- **うまくいかなかったこと**: Runbook に、ウィザードの落とし穴の警告がなかった（作った側の記述の不足）。コントローラーが、止まる対象の先にあり、直せなかった。夜間に、物理的な確認の手段（モニターとキーボード）が、すぐ使えなかった。
- **運が良かったこと**: データ損失がなかった。Mac を `1.1.1.1` にすれば、インターネットは使えた。
