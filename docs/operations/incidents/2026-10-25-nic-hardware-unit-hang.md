## 要約

スマホを Wi-Fi に繋ぐと homelab もインターネットも使えず、モバイル回線なら繋がった。
Mac からはルーター（`192.168.11.1`）に届いたが、PVE（`.10`）と全 VM は ping も ARP も応答しなかった。
電源・LED・ケーブルは正常だった。強制再起動で復旧した。

前回起動のログに、NIC ドライバの `Detected Hardware Unit Hang` が **22:29:17 から 1198 回**続いていた。NIC の送信が止まり、ホストが LAN から消えていた。
Slack に何も届かなかったのは、**監視 VM も同じホストの上にあり、NIC が止まれば通知も出せない**ため。[ADR-0002](../../adr/0002-no-external-monitoring.md) で受け入れたリスクが、実際に起きた。

## 2. 調査結果

### 2.1 切り分け

| 確認 | 結果 | 分かったこと |
| --- | --- | --- |
| Mac（有線）から `1.1.1.1` に ping | 通る | 回線とルーターは生きている |
| `.1`（ルーター） | 応答 | ルーターは生きている |
| `.10`、`.11`、`.13`、`.20`、`.22` | ping 不通。ARP は `(incomplete)`（同じ LAN の `.60` 台の端末は ARP が取れる） | L2 で応答がない。VM は PVE の仮想ブリッジ越しなので、**ホストの NIC かブリッジが LAN に出ていない** |
| `dig @192.168.11.11` | タイムアウト | AdGuard に届かない。これがスマホ・Wi-Fi 端末のインターネット不通の理由 |
| PVE の LED・電源・ケーブル | 正常 | 電源断ではない。NIC か OS の問題 |

### 2.2 原因の特定（再起動後に前回起動のログを確認）

```text
e1000e 0000:00:1f.6 nic0: Detected Hardware Unit Hang:
  TDH <b2>  TDT <ce>  next_to_use <ce>  next_to_clean <b1>
  ...
```

- `TDH`（送信ヘッド）が進まない。NIC が送信キューを処理できなくなった状態。
- 22:29:17 から数秒おきに繰り返し、リンクが戻らないまま強制再起動まで続いた。
- NIC は Intel I219（`e1000e`、カーネル `6.17.2-1-pve`）。Intel の I219 系で、TSO（TCP セグメンテーションオフロード）を有効にしていると起きる Hardware Unit Hang は、広く知られている。
- 対応前の設定は `tcp-segmentation-offload: on`、`generic-segmentation-offload: on`、`generic-receive-offload: on`。
- **推定**: 今回の原因は TSO を含むオフロード。確定にするには、無効化後に再発しないことを時間をかけて確認する必要がある。107 日の連続稼働のあとで初めて起きており、トリガー（負荷・特定の通信）は特定できていない（**未確認**）。

### 2.3 なぜアラートが飛ばなかったか

- Prometheus、Alertmanager、blackbox-exporter は、すべて vm-monitoring の上で動く。
- ホストの NIC が止まると、vm-monitoring は Slack に通信できない。また、Prometheus が `TargetDown` を検知しても、通知の送り先に出られない。
- 外形監視（blackbox）も同じ VM から発信するので、検知できない。
- これは [監視・アラートの「限界」1・2](../../services/monitoring.md#限界既知の弱点) と、[ADR-0002](../../adr/0002-no-external-monitoring.md) で受け入れたリスクの通り。**再検討の条件（再び監視 VM を巻き込む障害が起きた場合）に該当した**。

### 2.4 なぜインターネットまで使えなくなったか

- ルーターの DHCP が配る DNS は、vm-infra（AdGuard、`192.168.11.11`）を指していると推定している（**未確認**。ルーターの設定は見ていない）。Mac の DNS も `192.168.11.11` の次が `1.1.1.1` だった。
- vm-infra が応答しないと、名前解決ができず、Wi-Fi の端末はインターネットも使えない。モバイル回線は別の DNS を使うので繋がった。

## 3. 復旧

1. PVE 機を強制再起動する（電源ボタンの長押し）。モニターを繋げなかったので、画面の状態は確認していない。
2. `onboot=1` の VM が `startup` の順序で起動する。vm-infra が起動した時点で DNS が復旧する。
3. `qm list` で VM、`ping` と `dig @192.168.11.11` で DNS を確認する。

## 4. 恒久対応

### 4.1 NIC のオフロード無効化（適用済み）

`ansible/roles/proxmox/tasks/main.yml` に次を追加した。

| タスク | 内容 |
| --- | --- |
| `/etc/network/interfaces` の `iface nic0` に `post-up ethtool -K nic0 tso off gso off gro off` を追加（`blockinfile`） | 再起動後も有効にする |
| `ethtool -K nic0 tso off gso off gro off` を実行 | 今の実行中の NIC に即時反映する。`ifreload` は通信が途切れうるので使わない |

- 実機で `ethtool -k nic0` により 3 つとも `off` になったことと、`ifquery --check nic0` が `pass` であることを確認した。
- ソフトウェアの負荷が増える（TSO を CPU で処理する）が、1Gbps の個人用途では無視できる範囲と見ている。
- **未確認**: `post-up` が再起動後に実際に効くこと。次回の PVE 再起動のあとに `ethtool -k nic0` で確認する。

### 4.2 外部 Heartbeat の導入（未完）

[ADR-0002](../../adr/0002-no-external-monitoring.md) の案 A。`Watchdog` を外部サービスへ定期送信し、途絶えたら外部から通知する。ホストの停止、NIC の停止、回線断を、ホストの外から検知できる。
サービスの選定、秘密情報（ping URL）の管理、ADR-0002 を置き換える ADR の追加は、別の変更で行う（§5 の #2〜#4）。

## 6. ポストモーテム

### 6.1 影響

- 全 VM（vm-infra、vm-monitoring、vm-apps、vm-code）と PVE が、約 40 分以上（22:29〜23:10 の間）LAN から到達できなかった。
- Wi-Fi の端末は DNS の停止でインターネットにも出られなかった。
- 通知が 1 通も届かず、**人が気づくまで検知できなかった**。

### 6.2 うまくいったこと / いかなかったこと / 幸運だったこと

| 区分 | 内容 |
| --- | --- |
| うまくいった | ARP の状態から、VM 個別でなくホストの NIC の問題だと早く絞り込めた |
| うまくいった | ホストの OS は生きていたので、再起動後に journald の前回起動のログから原因を特定できた |
| いかなかった | ホストの NIC 停止は、設計上どの通知にも出ない。ADR-0002 の「症状で気づく」に頼る形になった |
| いかなかった | DNS がインターネットの利用まで巻き込んだ（単一障害点） |
| 幸運だった | 強制再起動で全 VM が正常に起動し、データ損失が起きなかった |
| 幸運だった | ジャーナルが永続化されていて、再起動後も前回のログが残っていた |

### 6.3 教訓

1. **監視は、監視対象と同じ障害で一緒に止まる場所に置かない。** ホストの外から見る手段（Heartbeat）が必要だった。
2. **受け入れたリスクの再検討の条件は、起きたら実行する。** ADR-0002 の条件に今回該当した。
3. **NIC の送信停止は、電源・LED が正常でも起きる。** 物理の確認だけで判断せず、ARP の状態（L2 の応答）を見る。
4. **DNS を 1 台に集中させると、その停止がインターネットの利用まで止める。** セカンダリを検討する。
