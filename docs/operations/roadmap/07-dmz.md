# DMZ と外部公開（ハニーポット・Web サーバー）

[ロードマップ](README.md)の大型計画。未着手。外部に触れるものを置くための DMZ の VLAN を作り、ハニーポットや公開用の Web サーバーを置く。ハニーポットでは外部からの攻撃（狙われるポート、ログイン試行、実行されるコマンド）を実データで観察する。ネットワーク、セキュリティ、可観測性を合わせて学ぶ。方式を決めて導入に進むときは、設計書（`docs/architecture/`）と構成図の更新、ADR の追加を同じ変更で行う。

## 目的

- 外部に触れるものを内部から隔離する DMZ を設計し、検証する
- ハニーポットで、外部からどんな攻撃が来るかを実データで観察する
- Web サーバーなどを外部に公開できる置き場所を用意する
- 攻撃ログを Loki と Grafana で可視化し、既存の監視に統合する

## 基本方針

- DMZ のものが侵害されても、家庭内の LAN に届かない構成を前提にする。届かないことを検証してから、外部に公開する
- 公開の有無にかかわらず、まず DMZ と Cowrie（SSH / Telnet のハニーポット）を作り、Grafana で見る。T-Pot や Dionaea などは、運用に慣れてから検討する
- ハニーポットは、DMZ から外部への通信を原則禁止する。侵害されたハニーポットが、第三者への攻撃の踏み台になるのを防ぐ
- 公開用の Web サーバーは、ハニーポットと許可する通信が異なる（更新や Tunnel のために外向きの通信が要る）。同じ DMZ に置くか、分けるかは、Phase 1 で決める
- ER605 + SG2210P の VLAN とファイアウォールルールで実現する。OPNsense の導入を待たない

## 前提

- 進める順序は、(1) ER605 と SG2210P を導入する（Omada の段階 1〜2）、(2) VLAN 化する（段階 3）、(3) DMZ と Cowrie を検証する（Phase 1〜3。追加のハードは不要）、(4) [ネットワーク通信の収集・可視化](06-network-traffic-analysis.md)の受信用ホストの購入を判断する。DMZ 専用の機器への移行や VPS の利用は、外部公開（Phase 4）の前に決める
- [Omada 導入・VLAN 化](04-network-omada-vlan.md)の段階 3 まで（ER605、SG2210P、VLAN の切り替え）を終える
- DMZ は VLAN70（`10.77.70.0/24`）。[VLAN 設計](../../architecture/08-vlan-design.md)と [ADR 0022](../../adr/0022-vlan-set-and-ids.md) に反映済み。VLAN とルールは段階 3 で作り、置くものはこの計画で追加する
- コントローラーモードの ACL で LAN→LAN を制限できることを実機で確認する（公式 FAQ では可能。[VLAN 設計](../../architecture/08-vlan-design.md)の未決事項）。DMZ → 内部の遮断はこれに依存する。使えない場合は、スイッチの ACL などの代替を先に決める
- 管理画面の外部到達（Caddy 経由）は、公開するものを置く前（Phase 4 の前）に、Tailscale の ACL で整理する（VLAN 設計の未決事項）
- 現在は二重 NAT 環境で、外からポート開放ができない（VLAN 設計の前提）。外部公開は、次の「外部に公開する経路」のいずれかで行う

## 外部に公開する経路

二重 NAT では、家のルーターへのポート転送で公開できない。外向きに接続を張る方式を使う。

| 対象 | 経路 | 内容 | 論点 |
| --- | --- | --- | --- |
| Web サーバー（HTTP / HTTPS） | Cloudflare Tunnel | DMZ の `cloudflared` が Cloudflare へ外向きに接続する。ポート開放も公開 IP も要らず、引っ越し後も変わらない | [ADR 0005](../../adr/0005-tailscale-only-remote-access.md) を見直す（新しい ADR を追加し、古い方を「置き換え済み」にする）。独自ドメインと Cloudflare の設定。`cloudflared` の外向きの通信の許可 |
| ハニーポット（SSH など生の TCP） | VPS 上に置く | VPS の公開 IP で受け、ログだけ自宅の Loki へ送る | 最も安全。DMZ の学習にはならないので、自宅の DMZ での検証（Phase 1〜3）と併用する |
| ハニーポット（SSH など生の TCP） | VPS からトンネルで自宅の DMZ へ転送 | VPS の公開 IP で受け、WireGuard や Tailscale で自宅の Cowrie に転送する。接続は自宅から外向きに張る | 攻撃が家まで届く。DMZ → 内部の遮断が確実なことが前提。VPS の IP が踏み台にされないか確認する |
| ハニーポット（HTTP 系） | Cloudflare Tunnel | Web 向けのハニーポット（Snare / Tanner など）を DMZ に置き、`cloudflared` 経由で受ける。**VPS が要らない**。生の TCP（SSH など）は受けられない | Cloudflare 側のボット対策で攻撃の一部が弾かれ、見える量が減る。ハニーポットを通す運用が規約上問題ないか確認する。攻撃を受けるのは家の機器になる |
| 直接公開 | ポート転送 | 公開 IP が使える環境（引っ越し後など）で行う | 上流の環境が分かってから |

Tailscale Funnel や Cloudflare Tunnel は、不特定多数の生の TCP を受けるハニーポットには向かない。

**VPS を使わない場合の整理**: SSH などの生の TCP を不特定多数から受けるには、公開された TCP の入口が要る。二重 NAT の間は、VPS（またはそれに代わる TCP トンネルのサービス）が要る。VPS なしで進めるなら、次のいずれかになる。

- HTTP 系のハニーポットを Cloudflare Tunnel で受ける（上の表）。
- 公開 IP が使える環境（引っ越し後など）まで、SSH のハニーポットは公開せずに内部で検証する。
- LAN の内側に置く検知用のハニーポット（OpenCanary など）で、侵害された機器からの内部スキャンを検知する。インターネットからの攻撃は観察できないが、費用も公開のリスクもない。

## ファイアウォールの方針

| 通信の方向 | 方針 |
| --- | --- |
| Internet → DMZ | 公開するポートだけ許可（Tunnel なら不要） |
| DMZ → Trusted / Lab / IoT / Guests | 全拒否 |
| DMZ → Servers / Management | 原則拒否 |
| DMZ → Internet | ハニーポットは原則拒否。Web サーバーと `cloudflared` は、必要な宛先・ポートだけ許可 |
| 管理端末 → DMZ | 管理用のポートだけ許可 |
| DMZ → ログ収集先 | 必要な宛先・ポートだけ許可。または管理側から取得する |

ログの転送は、DMZ から収集サーバーへ最小限の通信を一方向に許可するか、管理側からログを取りに行く構成にする。後者のほうが DMZ からの通信を減らせる。

## DMZ に置くもの

### ハニーポット

| 候補 | 内容 | 見る点 |
| --- | --- | --- |
| Cowrie | SSH / Telnet のハニーポット。ログイン試行、入力コマンド、セッションを記録する | 最初の 1 台。軽い |
| T-Pot | 複数のハニーポットを統合したプラットフォーム。Web UI で攻撃傾向を分析する | リソース消費が大きい。メモリの配分を先に見積もる |
| Dionaea | サービスへの攻撃とマルウェアを収集する | 収集物の取り扱いに注意が必要 |
| Snare / Tanner | Web アプリを模倣するハニーポット。HTTP 系の攻撃を記録する | Cloudflare Tunnel で受ける案で使う。未検討 |
| OpenCanary | 内部ネットワーク向けの検知用ハニーポット。SSH、HTTP、SMB などを模倣し、触られたら通知する | インターネットに公開しない使い方。未検討 |

### 公開用の Web サーバー

- 何を公開するかは未定。公開するものごとに、必要な外向きの通信と、更新の方法を決める
- 公開するものにシークレットがある場合は、SOPS で管理する（リポジトリは公開）
- DMZ の VM の Terraform / Ansible での管理方法を決める

## ログの可視化

```plaintext
Cowrie → Alloy / Vector など（収集・正規化） → Loki（保存・検索） → Grafana（ダッシュボード・アラート）
```

見る項目: 攻撃試行数の時系列、送信元 IP、ユーザー名・パスワードの試行傾向、実行されたコマンド。既存の Grafana（`vm-monitoring`）に統合し、[ネットワーク通信の収集・可視化](06-network-traffic-analysis.md)とは別のデータソースとして並べる。

## 注意点

- DMZ を同じ Proxmox ホスト上の VM で作る場合、VLAN 分離だけでは、ホスト自体の侵害リスクは消えない。Proxmox の管理インターフェースを DMZ に出さず、仮想 NIC とブリッジの設定を確認する
- Tunnel を使っても、公開した Web サーバーに脆弱性があれば侵害される。
- 同じ Proxmox ホスト上に DMZ を置く間のホスト侵害の影響と緩和策は、下の「ホストが侵害されたときの影響」に整理した（検討中）。DMZ から内部への遮断が最後の防御になる
- 収集したログや収集物（マルウェアなど）の保存先と保存期間を決める。保存先は Git に入れない（リポジトリは公開）
- ISP や建物の規約で、外部公開やトンネルの利用が制限されていないか確認する

## ホストが侵害されたときの影響（検討中）

**状況**: 採用前の検討。採用したら、`docs/architecture/04-reliability.md` などの設計書に移し、必要なら ADR を追加する（[文書の運用](../../README.md#文書の運用)）。

DMZ の VM から Proxmox ホストが侵害された場合（VM 脱出など）の影響範囲と、同じホストに置く間の緩和策。最終的にはホストを分ける（[ADR 0016](../../adr/0016-dmz-placement.md)）。

### 影響範囲

| 見られる・触れるもの | 内容 |
| --- | --- |
| 全 VM のディスクとメモリ | `vm-infra`、`vm-monitoring`、`vm-apps`、`vm-code`、`vm-dev` の中身。メモリ上の秘密を含む |
| VM に置いた秘密 | API トークン、Cloudflare の資格情報、Git の認証情報、SSH 鍵など |
| `vm-infra` の DNS ログ | AdGuard の問い合わせ履歴。見えるのはドメインまで。検索語やページの内容は、HTTPS なので見えない |
| `vm-infra` の Tailscale 鍵 | tailnet に参加できる。ACL が緩いと Mac などに届く |
| Management VLAN | Omada コントローラー（ルーター・スイッチ・AP の設定を握る）に攻撃できる位置に立つ |

Mac やスマホのファイルは、ホストを通らないので直接は見られない。ただし、上の足場から連鎖して届く可能性はある。

### 緩和策（案）

- 仮想デバイスは virtio に統一し、CD-ROM・USB・シリアルなどの不要なデバイスを外す。DMZ の VM では `qemu-guest-agent` の要否を決める
- Proxmox と QEMU を定期的に更新する。DMZ の VM に CPU・メモリの上限を付ける
- VM への SSH で `ForwardAgent` を使わない
- Tailscale の ACL で、`vm-infra` から他の端末への新規接続を許可しない
- AdGuard のクエリログの保存期間を短くする
- VM に置く API トークンは、必要な操作だけを許可したものにする
- Omada の管理者に強いパスワードを設定し、2 要素認証が使えれば使う
- DMZ → 内部の遮断が実際に効くことを、公開前に `nmap` などで確かめる

### ホストを分けたとき

守りの要が、ホストの設定から ER605 の ACL とスイッチのポート設定に移る。専用機のポートは access ポート（DMZ の VLAN のみ）にし、秘密を置かず、家の Tailscale に参加させない。

## 段階

### Phase 1: 隔離ネットワークを作る

- [ ] DMZ のファイアウォールルールの詳細を設計し、VLAN 設計に反映する（VLAN とアドレスは決定済み）
- [ ] ハニーポットと Web サーバーを同じ DMZ に置くか、分けるかを決める
- [ ] DMZ の VM は、まず Proxmox の同じホストで、インターネットに公開しない範囲で検証する。将来は別の小型 PC やラズパイなどを DMZ 専用にする。別の機器へ移す時期（外部公開の前か）を決める
- [ ] DMZ → 内部 LAN の通信が遮断されていることを検証する（インターネットには公開しない）
- [ ] 「ホストが侵害されたときの影響」の緩和策のうち、採用するものを決める。採用したら設計書に移す

### Phase 2: Cowrie を VM に導入する

- [ ] DMZ に VM を作り、Cowrie を入れる
- [ ] テスト端末から SSH 接続し、認証ログとコマンドログが取れることを確認する
- [ ] 設計書・構成図を更新する

### Phase 3: 可視化

- [ ] Loki + Grafana で攻撃ログを可視化し、アラートを設定する
- [ ] [監視](../../services/03-monitoring.md)の文書と「容量の上限設定」を更新する

### Phase 4: 外部に公開する

- [ ] ハニーポット: 公開の経路を選ぶ（VPS に置く、VPS から DMZ へ転送する）。公開を止める手順を先に決めておく
- [ ] Web サーバー: 公開するものを決め、Cloudflare Tunnel の ADR を追加する（ADR 0005 を置き換え済みにする）
- [ ] VPS を使う場合は、費用の目安と、事業者がハニーポットの運用を認めているか（利用規約）を確認する
- [ ] 管理画面の外部到達を Tailscale の ACL で整理する（公開の前提）
- [ ] ISP の制約、出口の制御、隔離のテストを確認してから公開する

### Phase 5: 発展

- [ ] Suricata による IDS、T-Pot、攻撃傾向の分析、検知ルールの作成へ広げる
