# ネットワーク通信の収集・可視化

[ロードマップ](README.md)の大型計画。未着手。自宅ネットワークを流れる通信を可視化・記録・分析し、自宅 Wi-Fi の各端末が「いつ、どこに、どのような通信をしているか」を Web UI で確認できるようにする。方式を決めて導入に進むときは、設計書（`docs/architecture/`）と構成図の更新、ADR の追加を同じ変更で行う。

## 目的

- 端末ごとのアクセス先（宛先 IP・ドメイン・ポート）と通信量を把握する
- 通信の中身（プロトコル、可能な範囲のペイロード）を調べられるようにする
- 想定外の通信（IoT 機器の外部通信、未知の宛先など）に気づけるようにする
- ネットワークの監視・分析技術を学ぶ

## 機能要件

| ID | 要件 | 優先度 |
| --- | --- | --- |
| F-01 | 自宅 LAN からインターネットへ出ていく通信を監視できる | Must |
| F-02 | Wi-Fi 端末を含む各端末の通信を識別できる | Must |
| F-03 | 送信元・宛先 IP、ポート、プロトコルを確認できる | Must |
| F-04 | 通信先のドメイン名や Web サービスを可能な範囲で識別できる | Must |
| F-05 | 端末別・通信先別の通信量を可視化できる | Must |
| F-06 | ブラウザからダッシュボードを閲覧できる | Must |
| F-07 | 過去の通信履歴を検索・分析できる | Must |
| F-08 | パケットを取得・保存し、Wireshark などで詳細解析できる | Should |
| F-09 | 通信異常や不審な接続先を検出できる | Should |
| F-10 | Grafana など既存の監視基盤と連携できる | Could |
| F-11 | 閲覧した Web ページの URL や内容を識別できる | Could（技術的制約あり） |

F-11 は HTTPS で URL のパス、検索キーワード、ページ本文が暗号化されるため、通常のパケット監視だけでは実現できない。取得できるのは、宛先 IP、DNS の問い合わせ、TLS の SNI までを基本とする。

## 非機能要件

| 分類 | 要件 |
| --- | --- |
| 可用性 | 監視基盤の停止が通常のインターネット通信に影響しない |
| 性能 | 通常の家庭内通信を、大きなパケット欠落なく観測できる |
| 拡張性 | 将来の OPNsense、VLAN、監視対象端末の追加に対応できる |
| 運用性 | Web UI で日常的な確認ができ、CLI からも詳細調査できる |
| 保存性 | 通信統計と PCAP を分けて、保存期間と容量を管理できる |
| セキュリティ | 監視 UI は LAN 内または VPN（Tailscale）経由に限定し、認証を設ける |
| プライバシー | 監視対象者への周知、アクセス制限、保存期間を設定する |
| コスト | 既存機材を優先し、追加ハードウェアを最小限にする |

## 構成上の制約

- OPNsense は当面導入しない。Phase 4 で改めて判断する
- 既存の Proxmox 環境と `vm-infra` を優先的に使う
- 可能な限りセルフホストで実現する
- 通常通信への影響を避けるため、受動的な監視方式（ミラーなど）を優先する
- Wi-Fi 端末の通信を監視するには、パケットを取る位置を設計する必要がある
- 進める順序は、(1) ER605 と SG2008P を導入する（Omada の段階 1〜2）、(2) VLAN 化する（段階 3）、(3) [DMZ と外部公開](07-dmz.md)の検証（Phase 1〜3）、(4) 受信用ホストの購入を判断する。新しいハードの購入は、ER605 と SG2008P 以外は最後に判断する。Phase 1（`vm-infra` での検証）は追加のハードなしで先に始められる
- ER605 の導入を先に行う。[Omada 導入](04-network-omada-vlan.md)の段階 1（ER605 への交換と Buffalo の AP モード化）と段階 2（SG2008P）を終えてから、Phase 2 に進む

## 最大の設計課題: Wi-Fi 端末の通信をどこで取るか

現状はルーター（Buffalo）の内蔵 Wi-Fi を使っている。Wi-Fi 端末の通信はルーターの内部で処理されるため、下流のスイッチ（SG2008P）のポートミラーリングでは取れない。ルーターの WAN 側で取る方法もあるが、NAT 後のため端末を区別できず、F-02 を満たさない。

| 方式 | 内容 | 論点 |
| --- | --- | --- |
| Buffalo を AP モードにして有線でスイッチにつなぐ | [Omada 導入](04-network-omada-vlan.md)の段階 1 で予定している構成。Wi-Fi 端末の通信もスイッチを通るため、ポートミラーリングで取れる | ER605 と SG2008P の導入が前提。ER605 を先に導入する方針なので、この方式を第一候補にする |
| 外付けの AP を使う | ルーター内蔵 Wi-Fi を止め、AP をスイッチ配下に置く | AP の追加購入。Omada の AP（段階 4）と重なる |
| ネットワーク TAP | 回線の途中に挟んで複製する | 機器の追加購入。故障時に通信が止まる機種がある |
| ルーターのフロー出力 | NetFlow / sFlow などをルーターから送る | Buffalo と ER605 が対応しているか確認する。パケットは取れない |

## 候補ツール

| 候補 | 役割 | 見る点 |
| --- | --- | --- |
| ntopng | フロー・パケットの可視化。端末ごとのアクセス先、プロトコル、通信量を Web UI で見る | Community 版で足りる機能の範囲。履歴の保存期間と検索の制限 |
| tcpdump / Wireshark | パケットの取得と詳細解析（F-08） | 常時保存の容量。取得する条件の絞り込み |
| Zeek | プロトコルごとの接続・DNS・TLS のログを生成する | ログの保存先と、Grafana などでの可視化 |
| Arkime | PCAP の保存と検索 | 容量と性能 |
| Suricata | IDS として不審な通信を検出する（F-09） | 負荷。誤検知の扱い |

## 段階

### Phase 1: 既存 VM で試す

- [ ] `vm-infra` に ntopng と tcpdump を入れ、Web UI とパケットキャプチャの基本機能を確認する
- [ ] 監視できる範囲を確認する（この段階では `vm-infra` が見える通信に限られる）
- [ ] 設計書・構成図・監視の文書を更新する

### Phase 2: 自宅ネットワーク全体の通信を取る

- [ ] 前提として、Omada の段階 1〜2（ER605、Buffalo の AP モード化、SG2008P）を終える
- [ ] 上の表から取得方式を決める（SG2008P のポートミラーリング、AP の構成、TAP を比較する）
- [ ] 収集する範囲、保存期間、HTTPS の扱い、監視対象者への周知を決め、ADR に残す
- [ ] ミラーポートに使う SG2008P のポートと、受信用ホストを置く VLAN を決め、[VLAN 設計](../../architecture/08-vlan-design.md)に反映する
- [ ] 受信用ホストを決める。第一候補は、Proxmox に USB NIC を足さず、NIC が 2 つ以上ある別の小型 PC（受信専用と管理用。Intel 製 NIC を優先）。OPNsense 用や DMZ 専用の機器とは兼用しない
- [ ] Wi-Fi 端末を含めて、端末を区別できることを確認する

### Phase 3: 監視・分析の高度化

- [ ] 必要に応じて Zeek、Arkime、Suricata、Grafana を追加し、履歴の検索、異常検知、通知を実装する
- [ ] 通信統計と PCAP の保存期間と容量を決め、[監視](../../services/03-monitoring.md)の「容量の上限設定」に追記する

### Phase 4: OPNsense との統合

- [ ] OPNsense の導入（[OPNsense 導入](08-network-opnsense.md)）後に、VLAN・Firewall・DNS・監視を統合する
- [ ] OPNsense 側での取得と Suricata の可否を判断する。受信用の別機器（Phase 2）を置き換えられるかも合わせて検討する

## 完了条件

- MacBook から Web UI にアクセスして、通信状況を確認できる
- 監視対象のスマホ・PC・VM を区別できる
- 各端末の通信先 IP、通信量、時刻を確認できる
- DNS や TLS から取得できる通信先ドメインを確認できる
- 過去の通信履歴を検索できる
- 必要な通信を PCAP で保存し、Wireshark で解析できる
- 監視用 VM を止めても、自宅のインターネット接続が続く
