# syslog によるネットワーク機器のログ収集

[ロードマップ](README.md)の記録。**検討中**で、採用は決めていない。設計書と ADR には、採用を決めるまで書かない。採用したら、詳細を設計書と ADR に移し、この文書は [02](02-completed.md) に 1 行だけ残す。

## 目的

ER605、SG2210P、Buffalo、Omada コントローラーのログを、`vm-monitoring` に集めて残す。これらの機器は、再起動するとログが消える。エージェントも入れられないので、外に出す手段は syslog に限られる。ER605・SG2210P の移行（[10](10-er605-sg2210p-migration-plan.md)）や VLAN 化、ACL の変更のときに、原因を追えるようにしたい。

## 見送り中の Loki との関係

[Loki + Grafana Alloy](03-deferred.md#loki--grafana-alloyログ収集基盤)は、全ホストの journald と Docker のログを集める計画として、見送っている。見送りの理由は、エージェントを全ホストに入れる手間と、thin pool の過剰割当だった。

この文書が扱うのは、その一部だけである。ネットワーク機器の syslog を受けるだけなら、全ホストにエージェントを入れる必要がない。ログの量も、ホスト全体に比べて小さい。ただし、Loki を `vm-monitoring` に置くことは同じなので、容量とメモリの条件は、見送りの理由と重なる。このため、syslog 収集を採用する場合は、03 の再検討の条件を満たしたものとして扱い、03 の項目を更新する。

## 案

収集と保存を分けて考える。

| 案 | 内容 | 長所 | 短所 |
| --- | --- | --- | --- |
| A | `vm-monitoring` で rsyslog を動かし、ファイルに書く。logrotate で容量と日数を抑える。 | 追加のコンテナがなく、軽い。 | 検索は `grep` になる。Grafana でメトリクスと並べて見られない。 |
| B-1 | Grafana Alloy が syslog を受け、Loki に送る。 | 将来、全ホストの journald と Docker のログに、同じエージェントで広げられる。ラベル設計の情報が多い。 | メモリを使う。RFC3164 に対応しているかは、使う版で要確認。 |
| B-2 | Fluent Bit が syslog を受け、Loki に送る。 | 軽い。RFC3164 と RFC5424 の両方を標準で受けられる。 | ログ専用で、メトリクスは別の道具が要る。 |

現時点の推奨は、**B-1（Alloy と Loki）**である。ただし、実機が RFC3164 でしか送れず、使う版の Alloy が対応していなければ、B-2 にする。A は、Loki の容量やメモリが負担になる場合の代替にする。

## 設計上の論点

保持期間は 14 日、容量の上限は 3GB 程度から始める案である。Loki は、`limits_config.retention_period` と、`compactor` の `retention_enabled` の両方を設定しないと、古いログを消さない。

ラベルは、`host`、`app`、`severity` のように少数に絞る。ログの本文をラベルにすると、Loki が重くなる。

UDP の 514 番は、認証も暗号化もない。受信できる送信元は、機器の IP だけに絞る。ゲートウェイの ACL は、2026-11-27 に絞った（[手順書 27](../runbooks/27-network-acl-tighten.md)）。Management から Servers への通信は、末尾の拒否（`910`）で止まるので、機器から `vm-monitoring` の 514 番への許可を、`910` より上に足す（[通信ポリシー](../../architecture/hld/05-network.md#通信ポリシー)の「Management → Servers」に書いてある）。ER605 自身が送る syslog が、LAN → LAN の ACL を通るかは、未確認である（ゲートウェイ自身の住所への通信は ACL の対象外だった）。SG2210P と `vm-omada` から送る分は、ACL を通る。

ACL のログ（検討中、2026-11-27 の見立て）: ゲートウェイ ACL のルールには、ルールごとに「ログ」の設定がある。有効にするには、サイトのリモートログ（ログ > 設定 > アドバンス > リモートログ）に、syslog の送り先を設定しておく必要がある。採用するなら、末尾の拒否（`9xx`）だけを有効にする案である。拒否のログがあれば、新しい通信が止まったときに ACL が原因かを見分けられ、Lab・IoT・DMZ の端末が他の VLAN をのぞく動きにも気づける。許可のルール（`1xx`）は、Prometheus の取得や Caddy の転送のように常に流れる通信に当たり、量ばかり増えるので、有効にしない。拒否のログが 1 日にどれだけ出るかは、未確認である。

受信側が、障害の影響を受けるネットワークの内側にあると、障害のあいだのログは届かない。NIC やリンクの断（[INC-2026-10-25](../incidents/2026-10-25-nic-hardware-unit-hang.md)）では、復旧後に追える範囲に限られる。
