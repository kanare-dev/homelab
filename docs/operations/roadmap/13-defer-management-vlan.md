# 管理系の VLAN10 化（段階 3b）の前提と未決事項

[ロードマップ](README.md)の記録。2026-11-09 に、段階 3 のリハーサル（[C-2](../runbooks/22-network-stage-3-rehearsal.md)）で、コントローラーの IP 変更に機器が付いてこない見込みが強まった。運用者が「一斉に切り替えることにこだわりはない」「最終的には管理系を VLAN10 にしたい」と述べたことから、**段階 3 では管理系を今の LAN に残し、VLAN10 化を別の段階にする**ことを採用した。

**状態:**

- **採用（未適用）**: 段階 3 の範囲の変更。決めたことは [ADR-0028](../../adr/0028-defer-management-vlan10.md)、[VLAN 設計](../../architecture/08-vlan-design.md#切り替え方式-一斉切り替え)、[移行計画](10-er605-sg2210p-migration-plan.md)の段階 3 に移した。この文書には、二重に書かない。
- **採用（未適用）**: 段階 3b の順序（**機器を先に VLAN10 へ移し、そのあとコントローラーを移す**。2026-11-19。[ADR-0031](../../adr/0031-stage3b-devices-before-controller.md)、手順は[段階 3b の作業](../runbooks/23-network-stage-3b-management-vlan10.md)）。下の「確かめる順序」の記録は、この決定に至った経緯。
- **検討中**: 段階 3b の時期と、ACL を絞る日の前に決める未決事項（[ADR-0029](../../adr/0029-stage3-acl-allow-all-then-tighten.md)）。下に書く。

## 最終形（確定）

**管理系は、最終的に VLAN10（Management）に置く。** 運用者が確定とした（2026-11-10）。理由は、構成がきれいになるから。コントローラーの住所の変更（C-2）が解決できるかは、まだ不安が残るが、解決の手段が見つからない場合の最終手段（機器のリセットと再採用）は、段階 1・2 で一度行った作業で、バックアップもあるので、行き止まりではない。

## 採用したことの要点

- 段階 3 では、管理系（Proxmox ホスト、`vm-omada`、ER605・SG2210P）の住所を変えない。そのほかを、予定どおり一斉に切り替える。
- 管理系は、段階 3 のあとの「段階 3b」で、Management（VLAN10）へ移す。最終形は変えない。

## 段階 3b の前提（検討中）

1. **機器の接続先（コントローラーの住所）を直す手段を整える。** 候補は、[移行計画](10-er605-sg2210p-migration-plan.md)の 3-A の「検討中」の案 A〜E（Linux の VM で Discovery Utility、Windows の PC、SSH の有効化、ER605 の静的ルート、再採用を前提にする）。仕事用 PC は使えない（運用者）。
2. **接続先を、IP ではなくホスト名にする。** たとえば `omada-ctl.lab.kanare.dev` のような名前にして、1 回だけ直せば、以降の IP の変更は、DNS の更新だけで済む。Discovery Utility の release note に「IP 形式の Inform URL に対応」とあるので、ホスト名が本来の形のはず（未確認。要検証）。
3. **`vm-omada` に、VLAN10 の NIC を足す。** 今の Terraform の VM モジュールは、NIC が 1 つで、`vlan_id` も無い（変更が要る）。NIC を足す `apply` は、VM の再起動を伴うことがある（[apply による再起動](../runbooks/15-terraform-apply-restart.md)）。
4. 順序（Proxmox ホスト、`vm-omada`、機器の管理 IP のどれから移すか）と、時期。未決。

### 確かめる順序（案。検討中）

実機に大きな変更を加える前に、軽い手段から順に確かめる。途中で手段が見つからなければ、そのとき、再採用で行くか、見送るかを決める。専用の道具を新しく用意する手は、最後に回す。

1. **コントローラーの画面を見る**（変更なし。**2026-11-17 に確認した**）: デバイスの追加に「手動で追加」「自動検索」「インポート」の 3 つのモードがある。「手動で追加」は、**「デバイス管理」を有効にしないと使えない**。「デバイス管理」は、全体の設定（グローバルビュー）の「システム設定」の「デバイス管理アクセス」にあり、「有効にすると、コントローラーは、リモート管理のために、デバイス管理ホスト名/IP を、管理対象デバイスに適用する」とある。有効にするとき、「このホスト名または IP がデバイスから到達可能であることを確認してください。そうでない場合、導入できない可能性があります」と確認が出る（確認は押さず、キャンセルした。有効にはしていない）。
   - **これが、機器の接続先を直す仕組みの本命**。コミュニティの報告（Controller V5 の 1 件。[Device Management IP/Hostname](https://community.tp-link.com/en/home/forum/topic/602092)）では、この設定を有効にすると、コントローラーが採用済みの機器に「新しい住所」を知らせ、機器が付いてくる。リセットは言及されていない。ただし、1 件の報告で、失敗の例も成功の確認も少ない。**実機で確かめる**。
   - **低リスクの確認（2026-11-17 に実施）**: 「デバイス管理アクセス」を、**現在の住所（`192.168.11.12`）のまま**有効にした（機器に伝わる住所は変わらない）。10 分間、ER605・SG2210P・Proxmox・`vm-omada`・インターネットへの到達を 1 秒ごとに監視して、失敗は 0 件。Omada の画面でも、ER605・SG2210P は「接続しました」・ヘルス「良好」のまま、アラートは `Watchdog` だけ。設定を機器へ配る仕組みは、この設定で壊れないことが分かった。**機器が、新しい住所に付いてくるかは、まだ確かめていない**（下の案）。保存（「適用」）は、2026-11-18 に確認した（スイッチがオンのまま、値が残っていた）。
   - 確かめ方の案（未実施。日時は未定。2026-11-17 に「また今度」とした）: (a) `vm-omada` に VLAN10 の NIC を足し、`10.77.10.3` を持たせる（旧 `192.168.11.12` は残す）。(b) ER605・SG2210P から `10.77.10.3` に届くことを、Omada のネットワークツール（ping）で確かめる。(c) 「デバイス管理アクセス」を有効にして、ホスト名/IP を `10.77.10.3` にする。(d) ER605・SG2210P が付いてくる（接続済みのまま）ことを確かめる。付いてこなければ、値を旧 `192.168.11.12` に戻す（`vm-omada` は両方の IP を持つので、戻せる見込み。ただし、付いていかなかった機器が、戻る保証はない。未確認）。(e) 付いてきたら、旧 NIC を外す。
   - **実施した（2026-11-18）。結果: 機器に新しい住所は伝わったが、接続は完了せず、旧住所に戻した。**
     - (a) Terraform（モジュールに任意の 2 枚目の NIC `extra_nic` を足した）で、`vm-omada` に `eth1`（VLAN10、`10.77.10.3/24`、ゲートウェイなし）を足した。VM が再起動し、cloud-init が新しいインスタンスとして再実行されて、SSH のホスト鍵が作り直された（`known_hosts` の更新が要った）。UFW に、機器向けの 3 ルール（8043/tcp、29810/udp、29811〜29816/tcp）の許可元として `10.77.10.0/24` を足した（Ansible）。
     - (b) ER605（`10.77.10.1` から）と SG2210P から、`10.77.10.3` への Ping は、4 回とも届いた。
     - (c) 「デバイス管理ホスト名/IP」を `10.77.10.3` にして適用した。既存の接続は、つなぎっぱなしのまま変わらなかった（再接続するまで、新しい住所は使われない）。
     - (d) 旧住所（`192.168.11.12`）宛を UFW で塞ぎ、コンテナを再起動した。UFW のログから、**ER605（`192.168.11.1`）と SG2210P（`192.168.11.62`）が `10.77.10.3` に接続を試した**ことが分かった（新しい住所は伝わる）。ところが、約 8 分待っても、`10.77.10.3` への接続は 1 本も完了しなかった。Omada の画面では、ER605 が「導入」、SG2210P が「導入できませんでした」だった。旧住所の拒否を外すと、約 1 分で、両方が旧住所で復帰した。
     - 原因は、未確認。有力な仮説は、**非対称ルーティング**（機器 `192.168.11.x` から来た接続の返事が、`vm-omada` の `eth0`（既定ルート）から、送信元 `10.77.10.3` で出て、ER605 に拒否される）。確かめるには、`vm-omada` の返事が出る経路を見る（`tcpdump`）。
     - 試験の設計の誤り: 旧 LAN の許可（送信元が `192.168.11.0/24`）を外す試験は、機器自身が旧 LAN にいる間は、新しい住所宛の接続も塞ぐので、意味がない。旧住所を外すなら、宛先（`192.168.11.12`）で塞ぐ。
     - 後始末: 「デバイス管理ホスト名/IP」は、`192.168.11.12` に戻した。`eth1` と、UFW の `10.77.10.0/24` の許可は、残している（旧住所には影響しない）。
   - **2 回目の試験（2026-11-18）。結果: 非対称ルーティングは事実だったが、直しても、機器は付いてこなかった。**
     - `tcpdump` で、機器（`192.168.11.1`・`192.168.11.62`）の SYN が `eth1` から入り、返事が `eth0` から出ていること（送信元は `10.77.10.3`）を確認した（このとき Omada は再起動中で、返事は RST）。
     - 実行時だけの policy routing（`from 10.77.10.3 lookup 100`、`default via 10.77.10.1 dev eth1`）を入れて、旧住所宛（`192.168.11.12` の 29810/udp、29811〜29816/tcp）を UFW で塞ぎ、コンテナを再起動した。約 4 分、機器の接続は 0 本。この間、機器から `10.77.10.3` に届いたのは UDP 29810（自動検出）の 2 本だけで、TCP 29814 の接続は無かった。再試行の間隔が長いだけの可能性も残る（区別できていない）。
     - 塞ぎを外すと、約 45 秒で、両方が旧住所に復帰した。policy routing は、後始末で外した（実行時だけの設定で、永続化していない）。
     - 結論: 機器が旧 LAN にいる間に、コントローラーの住所だけを動かす方式は、2 回の試験で成功していない。次の案（検討中。①は、[手順書の草案](../runbooks/23-network-stage-3b-management-vlan10.md)にした）: ①機器を先に VLAN10 へ移し、そのあとコントローラーを移す（有力。機器とコントローラーが同じネットワークになる）。②採用済みの機器に、コントローラーの住所を直接書き換える手段を探す。③機器を初期化して、新しい住所で採用し直す（バックアップから設定を戻す。停止が長い）。
   - ER605 は、DNS プロキシが内部の名前（`*.lab.kanare.dev`）を引けないので、ここでは、**ホスト名でなく IP で指定する**（ホスト名にするなら、ER605 が名前を引けるようにする必要がある）。
2. **DNS の名前と DHCP のオプション 138**: コントローラーを見つけるための名前（`omada_controller`）を、CoreDNS（Git と Ansible で管理）に足す。ER605 の DHCP に、オプション 138（コントローラーの IP）を載せる。機器が付いてくるか確かめる。採用済みの機器に効くかは未確認。段階 3 のあとなら、影響が小さい。
3. **割り切って、再採用を一度行う**: 時間を選び、バックアップを取って、メンテナンスとして行う（段階 1・2 で行った作業と同じ）。再採用で接続先が新しい住所に変わる。そのあと、2 の仕組みを整えておけば、将来の住所の変更は楽になる。
4. **Discovery Utility を、Linux の VM で動かす**（画面の転送が要る）: 1〜3 がすべてだめなときだけ。Mac では動かない（同梱の JavaFX が Windows 用）。

**調べたこと（2026-11-17。検索で見つけた資料。内容は、実機での確認が要る）**:

- DHCP のオプション 138 は、スイッチと AP に、コントローラーの IP を伝える仕組み。受け取った機器は、コントローラーの一覧に「保留（Pending）」で出る。ER605（ゲートウェイ）に効くかは、資料から読み取れなかった。
- コントローラーの IP が変わると、採用済みの機器は、コントローラーに接続できなくなる。公式の FAQ にも「接続に失敗するのは、IP を変えたので、普通」とある。コミュニティには、現地でのリセットと再採用だけが解決策だった、という報告が複数ある。公式の「採用済みのままで住所を直す」手順は、見つからなかった。
- 機器の画面（System > Controller Settings）や Discovery Utility で、Inform URL を設定できるが、採用済みの機器の画面には、入れない（2026-11-09 のリハーサルで確認済み）。
- 機器の IP が変わるときは、事前にコントローラーで、静的 IP を設定しておくのがよい（公式の FAQ）。
- 参考: [How to assign Static IP addresses for Omada Devices](https://www.tp-link.com/us/support/faq/3199/)、[change controller inform url/ip（コミュニティ）](https://community.tp-link.com/en/home/forum/topic/266288)。

したがって、上の 2（オプション 138）は、効かない可能性が高い。**1 の「デバイス管理アクセス」が効けば、再採用は要らない。** 効かなければ、3（再採用）を前提に、時間とバックアップを用意する。

あわせて、**機器がコントローラーを見失ったときの挙動**（最後の設定のまま動き続けるか。未確認）を確かめる。段階 3b の失敗の影響を決める。短い時間、コントローラーを止めて確かめる方法を考える。

本番の移行は、旧い住所を残したまま、新しい住所を足す（二重化）。機器が新しい側に付いてきたのを確かめてから、旧い住所を外す。途中で、いつでも戻せるようにする。

上の確認は、段階 3 の本番とは関係なく、段階 3 のあとに、時間のあるときに進められる。

## 既定の LAN のアドレス（検討中）

運用者の希望（2026-11-17）: 既定の LAN（VLAN1）を、`192.168.11.0/24` から `10.77.1.0/24` にしたい（to-be では使わない。アドレス体系 `10.77.<VLAN>.0/24` に合わせる）。

**判断（2026-11-17）: 段階 3b（管理系を VLAN10 へ）を先に行い、そのあとで、既定の LAN を `10.77.1.0/24` に変える。** 今すぐ `10.77.1.0/24` にすると、管理系の IP の付け替えが 2 回（`192.168.11.x` → `10.77.1.x` → `10.77.10.x`）になり、コントローラーの住所の変更（C-2）の問題が 2 回起きるため。サブネットの変更そのもの（案と確かめること）は、**検討中**で、採用していない。

- 前提: 管理系（Proxmox、`vm-omada`、ER605・SG2210P）が、今の `192.168.11.x` にいる間は、アドレスを変えられない。変えると、コントローラーの住所の変更（C-2）が絡む。したがって、**段階 3b（管理系を VLAN10 へ）のあと**の話になる。
- 案: 3b のあと、既定の LAN に、何も載っていない状態になる。そこで、既定の LAN のサブネットを、`192.168.11.0/24` から、アドレス体系（[ADR-0015](../../adr/0015-vlan-address-scheme-10-77.md)）に沿った `10.77.1.0/24`（VLAN ID 1 に合わせる）に変える。DHCP は止める。VLAN1 のネットワークは、Omada では消せないとみられる（未確認）。消せないなら、使わない状態で、別のアドレスにして残すのが、きれいな形になる。
- 確かめること: (1) Omada で、既定の LAN のサブネットを変えられるか（ゲートウェイの IP を変えるので、ER605 の LAN のアドレスも変わる）。(2) 変えた先に、何も載っていないこと（緊急用の入口 p6 は、native VLAN1 なので、この LAN に入る。緊急時の入口のアドレスも変わる）。(3) 旧アドレス `192.168.11.0/24` を、Tailscale の経路（`vm-infra` の `--advertise-routes`）、UFW の許可元、監視から外すこと。

## ACL を絞る日の前に決めること

**採用（2026-11-10）: 段階 3 の当日は ACL を全許可のまま切り替え、絞るのは別の日にする**（[ADR-0029](../../adr/0029-stage3-acl-allow-all-then-tighten.md)）。そのため、下の 2 つは、段階 3 の前提ではなく、ACL を絞る日の前提になった（段階 3 の完了から 2 週間以内を目安に、優先して行う（決定 2026-11-11））。

**決定済み（2026-11-10）: 今の LAN の DHCP が配る DNS は、ルーター（`192.168.11.1`）。** 段階 3 の間の今の LAN は、使う端末が少なく一時的なので、`vm-infra` が止まっても名前が引ける側に寄せた（[ADR-0028](../../adr/0028-defer-management-vlan10.md)）。ER605 の DNS プロキシが、今の LAN で外部の名前を引けることを確認した。

### 今の LAN の ACL（段階 3b までの暫定）

**検討中（案）。** 管理系が今の LAN（VLAN1、`192.168.11.0/24`）に残る間だけ使う、暫定のルール。[通信ポリシー](../../architecture/08-vlan-design.md#通信ポリシー)の許可表の「Management」を、「今の LAN」に読み替える。最終形のルールは設計書のとおりで、段階 3b で、VLAN10 向けに作り直す（下の「段階 3b での書き直し」）。暫定なので、設計書と ADR には書かず、ここに置く（運用者の判断。2026-11-10）。

名前と説明は、[ACL の名前と説明の付け方](../../architecture/08-vlan-design.md#acl-の名前と説明の付け方)に従う。宛先の「今の LAN」は、`mgmt` の代わりに `lan` と書く。説明の頭に `[暫定]` を付け、段階 3b のあとに探して消せるようにする。

| 順 | 動作 | 名前 | 送信元 | 宛先 | 中身 |
| --- | --- | --- | --- | --- | --- |
| 1 | 許可 | `130-servers-to-lan-caddy` | `vm-infra`（`10.77.20.10`） | `vm-omada`（`192.168.11.12`）の 8043、Proxmox（`192.168.11.10`）の 8006 | Caddy の `omada.lab`・`pve.lab` の転送 |
| 2 | 許可 | `131-servers-to-lan-metrics` | `vm-monitoring`（`10.77.20.11`） | 今の LAN の 9100 | Prometheus の取得（Proxmox、`vm-omada` の node_exporter）。ACL を絞る日は、`vm-omada` の UFW の許可元（下の「同じ日に直すコード」）と、合っていることを確かめる |
| 3 | 許可 | `151-trusted-to-lan` | Trusted | 今の LAN の 80/443/8006/22 | 管理ポートだけ（許可表の Trusted → Management） |
| 4 | 拒否 | `900-deny-from-lan` | 今の LAN | !今の LAN | 末尾。管理系から他の VLAN へは出さない。インターネット宛は止まらない（リハーサルの 5a〜5c で確認済みの形） |

- **今の LAN → Servers の許可（最終形の `110-mgmt-to-servers-dns`）は、作らない。** 今の LAN の DNS はルーターにしたので、`vm-infra` の 53 番が要らない。NTP も要らない見込み。`vm-omada` は `ntp.nict.jp`（Ansible の `ntp_servers`）で、インターネットから取る。Proxmox ホストの取得先は未確認（確かめる）。
- **Lab・IoT・Guests・DMZ → 今の LAN** は、各 VLAN の末尾の拒否（`940`〜`970`）で拒否される。今の LAN 向けのルールは要らない。
- **Trusted から Omada の画面（8043）を直接開く**ことは、許可しない（許可表のとおり）。Omada は Caddy 経由（`omada.lab.kanare.dev`）で開く。直接開く必要が出たら、3 に 8043 を足す。
- **ゲートウェイ自身（`192.168.11.1`）宛は、この ACL の対象外**（設計書の注意書きのとおり）。
- 確かめること: Caddy 経由の Omada・Proxmox の画面、Prometheus の `TargetDown` が出ないこと、Trusted の Mac から `ssh` で Proxmox に入れること、IoT の端末から今の LAN に届かないこと。

**同じ日に直すコード**: `vm-omada` の UFW は、Caddy からの 8043 を、`vm-infra` の旧アドレス（`192.168.11.11`）からだけ許可している（`ansible/inventory/group_vars/omada/vars.yml`）。段階 3 で `vm-infra` が `10.77.20.10` に移るので、**段階 3 のコードの準備で、`10.77.20.10` に直す**（直さないと、ACL と関係なく、`omada.lab.kanare.dev` が開けなくなる）。**9100（node_exporter）も同じ**: `vm-omada` の UFW は、`vm-monitoring` の旧アドレス（`192.168.11.13`）からだけ許可している（同じ `vars.yml` の 9 行目）。`vm-monitoring` が `10.77.20.11` に移るので、これも直す（直さないと、ACL が全許可でも、UFW で止まり、`vm-omada` の `TargetDown` が出る）。`vm-omada` は段階 3 で動かさないので、**直し忘れやすい**。`vm-infra`・`vm-apps`・`vm-code` の 9100 の許可も、同じ旧アドレスで書いてある（`group_vars/*/vars.yml`）ので、同じ作業で直す。機器のファームウェアの取得用の許可（`192.168.11.0/24` から 8043）は、機器が今の LAN に残るので、そのままでよい。

**段階 3b での書き直し**: 送信元・宛先の「今の LAN」を Management（VLAN10）にし、名前を設計書の例（`130-servers-to-mgmt-caddy` など）に戻す。宛先の IP も新しい住所（`10.77.10.3`、`10.77.10.10`）にする。最終形の `110-mgmt-to-servers-dns`（DNS・NTP）は、そのとき要るか決め直す。`[暫定]` のルールを消す。

### 緊急用の入口

**決定（2026-11-10）: SG2210P の p6 を、段階 3b までの緊急用の入口にする。** p6 は native が VLAN1 なので、挿した端末は今の LAN に入る。同じ VLAN の中の通信なので、ACL を通らず、`vm-infra` が止まっていても、Proxmox（`192.168.11.10`）、`vm-omada`（`192.168.11.12`）、ER605（`192.168.11.1`）に IP で届く。今の LAN の DHCP（`.60`〜`.99`、DNS はルーター）でアドレスを受け取る。

- 段階 3 で空きポートの設定を整理するときに、**p6 の native を VLAN1 から変えない**。Omada の操作でポートの設定が意図せず書き換わることがある（[2026-11-08 の障害](../incidents/2026-11-08-sg2210p-native-vlan-overwrite.md)）ので、ACL を絞る日の前に、挿して確かめる。
- p6 に挿した端末は、誰でも管理系に入れる。自宅の中なので、受け入れる。
- 段階 3b のあとは、VLAN10 の緊急用プール（`.240`〜`.250`。[ADR-0027](../../adr/0027-servers-octet-bands-and-emergency-dns.md)）を使う。p6 を VLAN10 の access にするかは、段階 3b で決める。
