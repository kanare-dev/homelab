# 管理系の VLAN10 化（段階 3b）の前提と未決事項

[ロードマップ](README.md)の記録。2026-11-09 に、段階 3 のリハーサル（[C-2](../runbooks/22-network-stage-3-rehearsal.md)）で、コントローラーの IP 変更に機器が付いてこない見込みが強まった。運用者が「一斉に切り替えることにこだわりはない」「最終的には管理系を VLAN10 にしたい」と述べたことから、**段階 3 では管理系を今の LAN に残し、VLAN10 化を別の段階にする**ことを採用した。

**状態:**

- **採用（未適用）**: 段階 3 の範囲の変更。決めたことは [ADR-0028](../../adr/0028-defer-management-vlan10.md)、[VLAN 設計](../../architecture/08-vlan-design.md#切り替え方式-一斉切り替え)、[移行計画](10-er605-sg2210p-migration-plan.md)の段階 3 に移した。この文書には、二重に書かない。
- **検討中**: 段階 3b（管理系を VLAN10 へ移す作業）の前提と、ACL を絞る日の前に決める未決事項（[ADR-0029](../../adr/0029-stage3-acl-allow-all-then-tighten.md)）。下に書く。

## 最終形（確定）

**管理系は、最終的に VLAN10（Management）に置く。** 運用者が確定とした（2026-11-10）。理由は、構成がきれいになるから。コントローラーの住所の変更（C-2）が解決できるかは、まだ不安が残るが、解決の手段が見つからない場合の最終手段（機器のリセットと再採用）は、段階 1・2 で一度行った作業で、バックアップもあるので、行き止まりではない。

## 採用したことの要点

- 段階 3 では、管理系（Proxmox ホスト、`vm-omada`、ER605・SG2210P）の住所を変えない。そのほかを、予定どおり一斉に切り替える。
- 管理系は、段階 3 のあとの「段階 3b」で、Management（VLAN10）へ移す。最終形は変えない。

## 段階 3b の前提（検討中）

1. **機器の接続先（コントローラーの住所）を直す手段を整える。** 候補は、[移行計画](10-er605-sg2210p-migration-plan.md)の 3-A の「検討中」の案 A〜E（Linux の VM で Discovery Utility、Windows の PC、SSH の有効化、ER605 の静的ルート、再採用を前提にする）。仕事用 PC は使えない（運用者）。
2. **接続先を、IP ではなくホスト名にする。** たとえば `omada-ctl.lab.kanare.dev` のような名前にして、1 回だけ直せば、以降の IP の変更は、DNS の更新だけで済む。Discovery Utility の release note に「IP 形式の Inform URL に対応」とあるので、ホスト名が本来の形のはず（未確認。要検証）。
3. **`vm-omada` に、VLAN10 の NIC を足す。** 今の Terraform の VM モジュールは、NIC が 1 つで、`vlan_id` も無い（変更が要る）。NIC を足す `apply` は、VM の再起動を伴うことがある（[apply による再起動](../runbooks/15-terraform-apply-restart.md)）。
4. 順序（Proxmox ホスト、`vm-omada`、機器の管理 IP のどれから移すか）と、時期。未決。

### 確かめる順序（案。検討中）

実機に大きな変更を加える前に、軽い手段から順に確かめる。途中で手段が見つからなければ、そのとき、再採用で行くか、見送るかを決める。専用の道具を新しく用意する手は、最後に回す。

1. **コントローラーの画面を見る**（変更なし）: デバイスの追加に、IP アドレスとデバイスアカウントで別のネットワークの機器を追加する「手動追加」があるか（Omada 6.3 で未確認）。
2. **DNS の名前と DHCP のオプション 138**: コントローラーを見つけるための名前（`omada_controller`）を、CoreDNS（Git と Ansible で管理）に足す。ER605 の DHCP に、オプション 138（コントローラーの IP）を載せる。機器が付いてくるか確かめる。採用済みの機器に効くかは未確認。段階 3 のあとなら、影響が小さい。
3. **割り切って、再採用を一度行う**: 時間を選び、バックアップを取って、メンテナンスとして行う（段階 1・2 で行った作業と同じ）。再採用で接続先が新しい住所に変わる。そのあと、2 の仕組みを整えておけば、将来の住所の変更は楽になる。
4. **Discovery Utility を、Linux の VM で動かす**（画面の転送が要る）: 1〜3 がすべてだめなときだけ。Mac では動かない（同梱の JavaFX が Windows 用）。

あわせて、**機器がコントローラーを見失ったときの挙動**（最後の設定のまま動き続けるか。未確認）を確かめる。段階 3b の失敗の影響を決める。短い時間、コントローラーを止めて確かめる方法を考える。

本番の移行は、旧い住所を残したまま、新しい住所を足す（二重化）。機器が新しい側に付いてきたのを確かめてから、旧い住所を外す。途中で、いつでも戻せるようにする。

上の確認は、段階 3 の本番とは関係なく、段階 3 のあとに、時間のあるときに進められる。

## ACL を絞る日の前に決めること

**採用（2026-11-10）: 段階 3 の当日は ACL を全許可のまま切り替え、絞るのは別の日にする**（[ADR-0029](../../adr/0029-stage3-acl-allow-all-then-tighten.md)）。そのため、下の 2 つは、段階 3 の前提ではなく、ACL を絞る日の前提になった（遅くとも段階 4 の前）。

**決定済み（2026-11-10）: 今の LAN の DHCP が配る DNS は、ルーター（`192.168.11.1`）。** 段階 3 の間の今の LAN は、使う端末が少なく一時的なので、`vm-infra` が止まっても名前が引ける側に寄せた（[ADR-0028](../../adr/0028-defer-management-vlan10.md)）。ER605 の DNS プロキシが、今の LAN で外部の名前を引けることを確認した。

### 今の LAN の ACL（段階 3b までの暫定）

**検討中（案）。** 管理系が今の LAN（VLAN1、`192.168.11.0/24`）に残る間だけ使う、暫定のルール。[通信ポリシー](../../architecture/08-vlan-design.md#通信ポリシー)の許可表の「Management」を、「今の LAN」に読み替える。最終形のルールは設計書のとおりで、段階 3b で、VLAN10 向けに作り直す（下の「段階 3b での書き直し」）。暫定なので、設計書と ADR には書かず、ここに置く（運用者の判断。2026-11-10）。

名前と説明は、[ACL の名前と説明の付け方](../../architecture/08-vlan-design.md#acl-の名前と説明の付け方)に従う。宛先の「今の LAN」は、`mgmt` の代わりに `lan` と書く。説明の頭に `[暫定]` を付け、段階 3b のあとに探して消せるようにする。

| 順 | 動作 | 名前 | 送信元 | 宛先 | 中身 |
| --- | --- | --- | --- | --- | --- |
| 1 | 許可 | `130-servers-to-lan-caddy` | `vm-infra`（`10.77.20.10`） | `vm-omada`（`192.168.11.12`）の 8043、Proxmox（`192.168.11.10`）の 8006 | Caddy の `omada.lab`・`pve.lab` の転送 |
| 2 | 許可 | `131-servers-to-lan-metrics` | `vm-monitoring`（`10.77.20.11`） | 今の LAN の 9100 | Prometheus の取得（Proxmox、`vm-omada` の node_exporter）。ACL を絞る日は、`vm-omada` の UFW の許可元（下の「同じ日に直すコード」）と、合っていることを確かめる |
| 3 | 許可 | `151-trusted-to-lan` | Trusted | 今の LAN の 80/443/8006/22 | 管理ポートだけ（許可表の Trusted → Management） |
| 4 | 拒否 | `900-deny-from-lan` | 今の LAN | !今の LAN | 末尾。管理系から他の VLAN へは出さない。インターネット宛は止まらない（リハーサルの 5a〜5c で確認済みの形） |

- **今の LAN → Servers の許可（最終形の `110-mgmt-to-servers-dns`）は、作らない。** 今の LAN の DNS はルーターにしたので、`vm-infra` の 53 番が要らない。NTP も要らない見込み。`vm-omada` は `ntp.nict.jp`（Ansible の `ntp_servers`）で、インターネットから取る。Proxmox ホストの取得先は未確認（確かめる）。
- **Lab・IoT・Guests・DMZ → 今の LAN** は、各 VLAN の末尾の拒否（`940`〜`970`）で拒否される。今の LAN 向けのルールは要らない。
- **Trusted から Omada の画面（8043）を直接開く**ことは、許可しない（許可表のとおり）。Omada は Caddy 経由（`omada.lab.kanare.dev`）で開く。直接開く必要が出たら、3 に 8043 を足す。
- **ゲートウェイ自身（`192.168.11.1`）宛は、この ACL の対象外**（設計書の注意書きのとおり）。
- 確かめること: Caddy 経由の Omada・Proxmox の画面、Prometheus の `TargetDown` が出ないこと、Trusted の Mac から `ssh` で Proxmox に入れること、IoT の端末から今の LAN に届かないこと。

**同じ日に直すコード**: `vm-omada` の UFW は、Caddy からの 8043 を、`vm-infra` の旧アドレス（`192.168.11.11`）からだけ許可している（`ansible/inventory/group_vars/omada/vars.yml`）。段階 3 で `vm-infra` が `10.77.20.10` に移るので、**段階 3 のコードの準備で、`10.77.20.10` に直す**（直さないと、ACL と関係なく、`omada.lab.kanare.dev` が開けなくなる）。**9100（node_exporter）も同じ**: `vm-omada` の UFW は、`vm-monitoring` の旧アドレス（`192.168.11.13`）からだけ許可している（同じ `vars.yml` の 9 行目）。`vm-monitoring` が `10.77.20.11` に移るので、これも直す（直さないと、ACL が全許可でも、UFW で止まり、`vm-omada` の `TargetDown` が出る）。`vm-omada` は段階 3 で動かさないので、**直し忘れやすい**。`vm-infra`・`vm-apps`・`vm-code` の 9100 の許可も、同じ旧アドレスで書いてある（`group_vars/*/vars.yml`）ので、同じ作業で直す。機器のファームウェアの取得用の許可（`192.168.11.0/24` から 8043）は、機器が今の LAN に残るので、そのままでよい。

**段階 3b での書き直し**: 送信元・宛先の「今の LAN」を Management（VLAN10）にし、名前を設計書の例（`130-servers-to-mgmt-caddy` など）に戻す。宛先の IP も新しい住所（`10.77.10.3`、`10.77.10.10`）にする。最終形の `110-mgmt-to-servers-dns`（DNS・NTP）は、そのとき要るか決め直す。`[暫定]` のルールを消す。

### 緊急用の入口

**決定（2026-11-10）: SG2210P の p6 を、段階 3b までの緊急用の入口にする。** p6 は native が VLAN1 なので、挿した端末は今の LAN に入る。同じ VLAN の中の通信なので、ACL を通らず、`vm-infra` が止まっていても、Proxmox（`192.168.11.10`）、`vm-omada`（`192.168.11.12`）、ER605（`192.168.11.1`）に IP で届く。今の LAN の DHCP（`.60`〜`.99`、DNS はルーター）でアドレスを受け取る。

- 段階 3 で空きポートの設定を整理するときに、**p6 の native を VLAN1 から変えない**。Omada の操作でポートの設定が意図せず書き換わることがある（[2026-11-08 の障害](../incidents/2026-11-08-sg2210p-native-vlan-overwrite.md)）ので、ACL を絞る日の前に、挿して確かめる。
- p6 に挿した端末は、誰でも管理系に入れる。自宅の中なので、受け入れる。
- 段階 3b のあとは、VLAN10 の緊急用プール（`.240`〜`.250`。[ADR-0027](../../adr/0027-servers-octet-bands-and-emergency-dns.md)）を使う。p6 を VLAN10 の access にするかは、段階 3b で決める。
