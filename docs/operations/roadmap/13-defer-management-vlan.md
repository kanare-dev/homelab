# 管理系の VLAN10 化を後回しにする案（検討中）

[ロードマップ](README.md)の記録。2026-11-09 に、段階 3 のリハーサル（[C-2](../runbooks/22-network-stage-3-rehearsal.md)）で、コントローラーの IP 変更に機器が付いてこない見込みが強まった。運用者が「一斉に切り替えることにこだわりはない。もっと楽な方法があれば、そちらでよい」「最終的には管理系を VLAN10 にしたい」と述べたことから、案をまとめた。

**状態: 検討中。採用していない。** 設計書・ADR・Runbook には反映しない。採用するかは、運用者が決める。

運用者の意向（2026-11-09）: 一斉切り替えが大変そうなら、**まず管理系は今の LAN に残して、そのほかの VLAN を整備し、最後に管理系を VLAN10 へ移す**、という段階に分けてもよい。条件つきの意向で、採用の決定ではない。採用する場合は、ADR を追加し、設計書・Runbook に反映する。

## 背景

段階 3 の現行計画は、アドレスの付け替えを 1 回にまとめ、**管理系も同時に新しい住所へ移す**（`vm-omada` を `10.77.10.3`、Proxmox ホストを `10.77.10.10`、どちらも VLAN10）。

リハーサルで分かったこと（詳細は[リハーサルの C-2](../runbooks/22-network-stage-3-rehearsal.md)）:

- 機器は、採用されたときのコントローラーの住所（`192.168.11.12`）を覚えている。
- 機器の接続先を直す手段が、今のところ見つかっていない。採用済みの機器の Web UI は 403、SG2210P は SSH が閉じている、Discovery Utility は Mac で動かない。
- 手段が決まらないまま `vm-omada` の IP を変えると、機器が管理者を見失い、ER605 のリセットと再採用（インターネットが止まる）になりうる。

## 案: 2 段階に分ける

| 段階 | 内容 | 時期 |
| --- | --- | --- |
| 1 | 管理系は、今の LAN（VLAN1、`192.168.11.0/24`）のまま残す。ほかを新しい VLAN へ一斉に切り替える | 段階 3 の本番 |
| 2 | 管理系を VLAN10 へ移す。機器の接続先を直す手段を整えてから、単独の作業として行う | 段階 3 のあと、時間のあるとき |

### 段階 1 で、変えるものと変えないもの

| | 内容 |
| --- | --- |
| **変えない** | Proxmox ホスト（`192.168.11.10`、タグなし）、`vm-omada`（`192.168.11.12`、タグなし）、ER605（`192.168.11.1`）、SG2210P（`192.168.11.62`）。機器の接続先は、そのまま |
| **変える** | `vm-infra`・`vm-monitoring`・`vm-apps`・`vm-code` を VLAN20、`vm-dev` を VLAN40。端末は VLAN30・50 |
| 使わずに置く | ER605 の VLAN10（Management。作成済み）。`vmbr0.10` は付けない |

この案では、段階 3 の Runbook の手順 3（Proxmox ホストを `vmbr0.10` へ）と手順 4（`vm-omada` を `10.77.10.3` へ）は、段階 1 では行わない。C-2 も、段階 1 には要らない。

### 段階 2 の前提（まだ決まっていない）

1. 機器の接続先を直す手段を用意する。候補は、[移行計画](10-er605-sg2210p-migration-plan.md)の 3-A の「検討中」の案 A〜E。
2. **接続先を IP ではなく、ホスト名にする**（たとえば `omada-ctl.lab.kanare.dev` のような名前）。1 回だけ直せば、以降の IP の変更は、DNS の更新だけで済む。Discovery Utility の release note に「IP 形式の Inform URL に対応」とあるので、ホスト名が本来の形のはず（未確認。要検証）。
3. `vm-omada` に、VLAN10 の NIC を足す（今の Terraform の VM モジュールは、NIC が 1 つで、`vlan_id` も無い。変更が要る）。

## 現行計画との比較

| | 現行計画（管理系も一斉） | この案（管理系を後回し） |
| --- | --- | --- |
| 本番当日の難所 | C-2（機器の接続先）。Proxmox ホストの `vmbr0.10` への移動 | なし（管理系は動かさない） |
| 失敗したときの影響 | 全体が止まりうる | 管理系の移動だけ。ほかの VLAN は動き続ける（機器が最後の設定のまま動く、は未確認） |
| 時間の制約 | 決めた時間内に終える | 段階 2 に期限がない |
| 手間 | 1 回 | 2 回（ACL などを、一度「管理系は VLAN1」で作り、あとで VLAN10 に書き直す） |
| 管理系の隔離 | 段階 3 で成立 | 段階 2 まで未成立（VLAN1 に残る） |

## 影響を受ける採用済みの決定

採用する場合、次を直す（新しい ADR を追加して、古い ADR を「置き換え済み」にする。[ADR の書き方](../../adr/README.md)）。

- [ADR-0004](../../adr/0004-vlan-cutover-all-at-once.md)（一斉切り替え）: 管理系を除く一斉切り替えになる。大筋は変わらない。
- [ADR-0023](../../adr/0023-proxmox-trunk-all-tagged.md)（Proxmox は全 VLAN をタグ付き）: 段階 1 では、ホストは、タグなしのまま。
- [ADR-0022](../../adr/0022-vlan-set-and-ids.md)、[ADR-0025](../../adr/0025-address-octets-by-role.md)、[ADR-0026](../../adr/0026-vmid-from-vlan-and-octet.md)、[ADR-0027](../../adr/0027-servers-octet-bands-and-emergency-dns.md): Management の住所、緊急用プールの扱い。
- [VLAN 設計](../../architecture/08-vlan-design.md)、[移行計画](10-er605-sg2210p-migration-plan.md)の 3-A・3-C、[段階 3 の Runbook](../runbooks/21-network-cutover-stage-3.md)の手順 3・4。

## 未確認・要判断

| 項目 | 内容 |
| --- | --- |
| 今の LAN の ACL | 管理系が VLAN1 に残るので、「Trusted → 今の LAN」の許可と、「今の LAN → 他」の拒否の設計を見直す（リハーサルの `rh-` の形が、そのまま使える見込み） |
| 今の LAN の DHCP の DNS | `vm-infra` が `10.77.20.10` に移るので、今の LAN の DHCP が配る DNS（今は `192.168.11.11`）を直す。SG2210P の DNS も |
| 緊急用の DHCP プール | Management（VLAN10、`.240`〜`.250`）は、VLAN10 に端末を繋ぐ口が無い間は、使えない。`vm-infra` が止まったときの非常用の入口を、どうするか（[ADR-0027](../../adr/0027-servers-octet-bands-and-emergency-dns.md)） |
| 機器の挙動 | コントローラーを見失った機器が、最後の設定のまま動き続けるか（未確認）。段階 2 の失敗の影響に関わる |
| ホスト名の Inform URL | 接続先を、ホスト名にできるか。ホスト名の名前解決が、機器の DNS で引けるか |
| 既定の LAN（VLAN1） | 段階 2 まで消せない。[移行計画](10-er605-sg2210p-migration-plan.md)の「既定の LAN の扱い」は、「当面、管理系が使う」に変わる |
| 管理系の隔離 | VLAN10 への隔離を、いつまでに済ませたいか（セキュリティ上の期限があるか） |
